# Backend memory

Durable lessons about the Go backend, kept for AI agents. Add one only when it is likely to matter again; fix stale facts instead of appending contradictions.

1. Migrations in `internal/platform/database/migrations/` are an append-only journal with checksums: never edit or delete an applied file; every schema or query change is a new numbered file. Startup fails if history was altered.
2. The server is its own OAuth 2.1 authorization server (`modules/oauth`) and hosts MCP spaces (`modules/space`; first is `modules/coding` at `/api/coding`). Tokens are opaque and stored hashed; a space accepts only tokens whose `resource` is its own URL. Features meet only in `internal/bootstrap/bridges.go`. Open endpoints (sign-in, sign-up, OAuth) stay rate limited via `bootstrap/limits.go`. Outgoing calls to person-chosen addresses (providers, CIMD) must use `platform/egress` (IP checked at dial time); hosted kinds have fixed addresses, gateways are loopback only.
3. Discovery contract: protected resource metadata at `/.well-known/oauth-protected-resource/api/<slug>`, server metadata at `/.well-known/oauth-authorization-server` and `openid-configuration`, CIMD (SSRF-guarded, public IPs only), DCR, PKCE S256, RFC 9207 `iss`. Keep `internal/bootstrap/e2e_test.go` passing when touching any of it.
4. A new space is a `space.Space` plus a bootstrap mount, never an `oauth` special case; the coding space is always on and strictly per person and per app: `bootstrap/connectedapps.go` maps the token's user id and client name to a project (`projectapp.ForApp`, `projects.source`, one live project per user and app) whose folder `agentTools.services` serves, the same path the agent uses (never share a folder, runner, or undo path across users or apps; the old `DATA_DIR/workspaces` is deleted at startup). Activity undo blobs are wrapped with the project id (`wrapUndo`). Tasks and `run_command` (bash, exec scope, asks every time) run only through `platform/sandbox`: one throwaway Docker container per run via the Engine API (`SANDBOX_IMAGE`, the shared toolbox image whose label `io.masihawam.toolchains` feeds the agent prompt; toolchains stay in the image, never per user; per-workspace `/cache` and `/run/egress` socket, removed by `Engine.Forget`; no network interface, `/tmp` must stay exec for Go/Java, read-only root, cap-drop ALL, no-new-privileges, memory/cpu/pids/fsize limits, workspace bind mount or data-volume `Subpath`, owner-labelled so startup cleanup only removes the server's own leftovers), under one shared `runner.Engine` that opens Docker lazily and never blocks startup. Tests that run tasks skip when no Docker daemon is reachable. `coding/domain.Tools()` is the single tool catalogue; calls pass permission, then scope, then run, are always logged, and no tool may reach `.workspace/` (task definitions). Write and run stay separate scopes, Off by default.
5. Adapters answer errors with `c.Status(n).JSON(httpserver.Failure(code))`; returning a wrapped error after writing a response makes Fiber overwrite it with a 500. There is no separate chat: every message is a `modules/task` thread, a run that changed nothing ends as an answer (`done`, no receipt), reads run unprompted and every write or run asks (`needsApproval`) unless the person set Skip approvals for the space. `coding/domain.Tools()` (including `start_site`/`stop_site`) is the one catalogue: the Spaces & tools switches gate the agent (`task` `ToolGate`: not offered, refused at call time) and MCP alike; an off tool is never bypassed. `start_site`/`stop_site` are not in `Tools()` (no toggle of their own); `codingdomain.SwitchOf` makes them follow `run_command`. Tests that run tasks must switch the changing tools on (`rigOn` does); they are off by default.
6. Sites (`modules/site`, `docs/sites.md`) serve untrusted code from the app's own origin, so isolation is browser-enforced and every layer stays on: `Content-Security-Policy: sandbox` without `allow-same-origin` on every `/run` answer (errors too; the app's own CSP is replaced), the Fetch Metadata guard in `RequireSession` (cross-site requests refused except navigations), the proxy dropping `Cookie`/`Authorization` going in and `Set-Cookie`/`Clear-Site-Data`/`Service-Worker-Allowed` coming out, hop-by-hop headers stripped before our own are added, and the destination always the site's own Unix socket. A login shell (`bash -l`, `sh -l`) resets PATH through `/etc/profile`, which hid cargo, rustc, go, java and mvn from a vendor program that runs commands that way even though the image has them; `sandbox/Dockerfile` writes `/etc/profile.d/toolchains.sh` and `scripts/smoke-test-sandbox.sh` checks both shells, so keep a new toolchain in both `sandbox.Path` and that file. A public site's login is held by a visitor pass (cookie on navigation, `X-Site-Visitor` header from the shim on the page's own requests): honor the cookie only on page navigations, never on other requests. The shim (`site/domain/shim.go`) rewrites `credentials: "include"` to `same-origin` and forces `withCredentials` off, because a credentialed request from the opaque origin fails against the wildcard `ACAO` (browsers refuse `*` with credentials) and answering `Access-Control-Allow-Origin: null` + credentials would let a sandboxed page read another project's private site with the owner's session. Never add `allow-same-origin`, never forward the session, never take host or port from the request. A private site keeps the app's login in `adapter/http/jar.go`: `Set-Cookie` is parsed and stored server-side per `site.Token|holder` (never per ticket string, which is re-minted on every owner visit), re-attached as `Cookie` toward the app, and still dropped from the browser answer; memory only, bounded, dies with the token. Preview hosts keep plain browser cookies instead; public sites have no jar yet. A sandboxed page's own requests carry no login, so private sites use `Site.Decide`: the signed-in owner always passes; anyone else passes only a non-page request with a valid ticket (HMAC of the token, the holder and an expiry, 4 hours, key made at startup, in the address as `/~<ticket>/`; the holder is the User-Agent, plus the client IP only when `CLIENT_IP_HEADER` is set, because behind a proxy without it every visitor shares one address); a page (GET navigation) always needs the owner and otherwise gets the 403 sign-in page. The uuid alone never opens anything, and `Sec-Fetch-*` headers are forgeable outside browsers, so never base private access on them alone; tests must cover forged headers. Visibility is changed only by the owner, never by an agent tool. Sites are one per project, manual stop only, capped per user and in total, and reset at startup. For full-stack previews, `SITE_PREVIEW_DOMAIN` provides opt-in isolated hosts (`docs/preview-auth.md`) and must be forwarded in compose files.
7. Verify site changes in a real browser, not only with Go tests: `make e2e-sites` starts the full app (real SPA, real container, `TestServeSiteForABrowser`) and runs `scripts/e2e-sites.ts` with a fresh signed-out Playwright browser (installed globally; scripts load it from `npm root -g`). It found what in-memory tests missed (a forged `Sec-Fetch-Dest` plus the address was enough to read a private site). Residual risk to keep documented: a ticketed address copied exactly, from the same User-Agent and IP, still loads sub-resources until it expires.
8. The runtime image is distroless (no curl, no shell), so its `HEALTHCHECK` is the binary itself: `agentic-ai-workspace healthcheck` (`platform/healthcheck`, wired in `cmd/workspace`) requests `/api/health` on `127.0.0.1:$PORT`. Compose inherits it, which is what makes `docker ps` say `(healthy)`; do not add a second healthcheck in the compose files.
9. GitHub (`modules/github`, Settings, Integrations) is a GitHub App user-to-server flow (web flow + PKCE, `state` single use and bound to the signed-in person). Tokens live sealed in `github_connections` (`platform/secretbox`); `ghu_` lasts 8 h and every refresh invalidates the old refresh token, so `Service.lock` serialises per person and a rejected refresh deletes the connection (a 5xx must not). A command gets the token only through `runner.GitSource`, bound per project in `bootstrap/github.go` (`useGitHub`): the owner comes from `projects.Owner(projectID)` at run time, never from the caller. The token goes in `GIT_CONFIG_*` env + `GH_TOKEN` (no file, no URL), only when the workspace has its proxy socket, with github hosts on a socket of its own (`Hub.Dir(id, extra...)` keys sockets by host set so a site and a command never flip each other's). Sites (`SiteSpec`) never get a token or the github hosts. A teammate running on a person's own plan (`plans.Run`, `taskcli_env.go`) does its shell commands inside the vendor program's container, not through `runner`: that container gets the github hosts and the same `GIT_CONFIG_*` env through `plans.gitOf` (set by `useGitHub`), or `git fetch` fails with `CONNECT tunnel failed, response 403` while a push through `run_command` works. Check which path a failing command took before blaming the token. Keep `bootstrap/github_test.go` and `application/*_test.go` passing when touching it.
9b. CI logs (`ci_logs`, `bootstrap/agenttools_cilogs.go`, `github/adapter/githubapi/logs.go`): `gh run view --log` in the sandbox fails with a bare 403 even though listing runs works, because the logs API answers 302 to a storage host (`pipelines.actions.githubusercontent.com` or `productionresultssa*.blob.core.windows.net`) that `runner/git.go` `githubHosts` does not allow, and the egress proxy refuses it (it now logs `egress refused a host`). Do not widen the allowlist: `*.blob.core.windows.net` is any account's storage, so a wildcard is an exfiltration path. The server fetches the log instead: token to `api.github.com` only, redirect followed by hand with no token over a `PublicOnly` client, the owner looked up from the project (never the caller), repo checked by `domain.LogRef.Valid`, output cut to the last lines. Listing a private repo's runs already needs Actions: read, so a working list means the permission exists; the lead must never tell the person to change a token scope. A tool the server runs reaches a teammate on a person's own plan (Codex, Claude Code) only if its name is in `siteToolNames` (`task/application/plansite.go`): the in-app loop and the MCP server do not cover that path, so a new server tool needs that entry and a `plansite_test.go` case, or the teammate answers that the tool is missing.
10. Context, not cost, bounds a task (`task/application/compact.go`). Never sum a task's usage against a cap: input tokens are re-counted every turn, so a long task trips it and Continue cannot recover (the old 400k `TokenCap` did exactly that). The size that matters is the last call's `Input+Output` against the model's window (`provider/domain/context.go`: chosen, else `[1m]` suffix, else 200K); past `window-33K` the model summarises (client-side, so every provider kind works) and `Block.Summary` marks the notes that replace everything before them in `sinceSummary`. Summarise only between tool rounds so tool_use/tool_result pairs stay whole, and treat a summary that calls a tool or is empty as a miss, never as a failure of the task.
11. Effort is `task/domain/effort.go` (`""`, low, medium, high, xhigh, max), stored per task and defaulted from `preferences.default_effort`; clients send it as `reasoning_effort` (OpenAI-style, incl. 9router) or `output_config.effort` (Anthropic) and omit it when empty, never a made-up default. Checked against a real 9router (`cx/gpt-6-luna`, Oct 2026): `reasoning_effort` reaches OpenAI, which accepts none, minimal, low, medium, high, xhigh, max and answers anything else with a 400 naming them (`param: reasoning.effort`), even though 9router's `/v1/models` says `thinkingEffortSupported: false`, so never trust that flag to hide the control. Which levels a model takes is the provider's call (the API returns `efforts` per model from `provider/domain/model.go` `EffortLevels`: a gateway that describes a model decides, a model reported as not reasoning gets none, `none` is dropped when it cannot switch thinking off, and a gateway that says nothing gets every level, so a provider added behind a gateway needs no code change; direct providers get their documented list; the UI never keeps its own list). A 9router gateway lists per-model `capabilities` at `/v1/models` without a key (`contextWindow`, `reasoning`, `thinkingEffortSupported`); its real window sizes differ from a 200K/1M guess (272K and 872K for `[1m]`), so `probe` reads them (`capabilities.contextWindow`, `context_length`, `context_window`, `max_input_tokens`) at Verify into `model_windows`; precedence is chosen (`model_settings`) > reported > `[1m]` > 200K, and Refresh in Settings re-reads them.
12. What 9router reports per model (`/v1/models`, no key needed) is read by `provider/adapter/probe` into `model_catalog` at Verify/Refresh (`Service.SyncStale` re-reads a gateway's list from `GET /api/providers` and `GET /api/models`, at most every 30 s per provider, in memory; it needs no Refresh, but a stale list was exactly why only Codex showed once Claude was connected; hosted providers are never re-read on a page load): `capabilities.contextWindow`, `reasoning`, `thinkingCanDisable`, and `thinkingFormat` (openai, claude-adaptive, claude-budget, gemini-*, deepseek, kimi, zai...; stored as `model_catalog.format`). 9router translates one OpenAI-style `reasoning_effort` for every backend and clamps what a model cannot take, so every format gets the full list except a `claude*` format, which gets Anthropic's low..max like 9router's dashboard does (decided from the reported format, never from a model or provider name). Its Claude (`cc/`) models answer with an event stream even when `stream` was not asked, so `openai.Client.Complete` falls back to reading SSE (`transport.ErrEventStream`); without that, compaction summaries on a Claude model failed. Test against the real gateway with `cx/`/`cc/` models before trusting a format guess.
13. 9router docs (README "Supported Providers"): a model id is `alias/model` (`cc/claude-opus-4-7`, `cx/gpt-5.5`, `kr/claude-sonnet-4.5`); groups are OAuth/subscription (Claude Code cc, Codex cx, GitHub, Cursor, Antigravity), Free (Kiro kr, OpenCode Free, Vertex), 40+ API-key providers (OpenRouter, GLM, Kimi, ...), custom OpenAI/Anthropic-compatible endpoints, and user-made combos (plain names, no slash). `/v1/models` reports `owned_by` per model (the alias); the friendly names (`display.name`, e.g. "OpenAI Codex") live only in 9router's source/dashboard API (`/api/providers`, 401 without a dashboard login), so we group by `owned_by` (`model_catalog.owner`, falling back to the id prefix). By the person's choice only three providers get a name, kept as copy in `web/.../content/models.ts` `gatewayProviderNames` (cx OpenAI Codex, cc Claude Code, oc OpenCode Free); every other alias shows raw, and the person declined naming more (too much to maintain), so do not grow that table without being asked. Models are never listed in code, for these three or any other: they come from the gateway and change. Only gateways are grouped: OpenAI labels everything `system`. OpenCode Free (`oc`, no auth) is missing from `/v1/models` on 9router 0.5.99: the fix that exposes no-auth providers (commit a8f63f4, 2026-10-15) is newer, so it appears after 9router is updated (our sync picks it up by itself), and even then its models can answer 403 `FreeTierError` (free tier only inside OpenCode). In zsh a loop variable named `path` clobbers `PATH`.
14. Jenkins (local, `jenkins` + `jenkins-docker` dind, job `agentic-ai-workspace` is an inline "Pipeline script", so a pushed `Jenkinsfile` changes nothing until the job config is updated). The Jenkins container has only git/curl/make/docker: Node and Go run in containers mounting `$WORKSPACE` at the same path (dind shares `/var/jenkins_home`); ports published by dind are reached at host `docker`, not 127.0.0.1. Credentials must sit in the System store, not the user store. The build version is `main.version` via `-ldflags` (Makefile `VERSION`, Dockerfile `ARG VERSION`), served as `X-App-Version` and in `/api/health`; `scripts/deploy-binary.sh` hot-swaps a folder-mounted binary (a single-file bind mount would keep the old inode).
15. Agent teams (`modules/agentteam` + `task/application/delegate.go`) must stay right-sized: the lead sizes a request first and small work never goes to teammates; teammates never talk to each other (the lead relays context and a shared plan); no cap on the number of jobs, only on idle ones in a row (`MaxIdleJobs`). Do not add peer chat, parallel code-writing teammates or extra roles to look thorough; the research behind this is in `agents/implementation-notes.md`, "The agent team".
16. Fiber v3 has no per-route `BodyLimit`: retain the global cap and narrowly change `fasthttp.Server.HeaderReceived` for the matching upload method, path and content type. The upload hook also requires a Cookie header, but runs before authentication; this leaves a known large pre-auth body risk. Do not enable `StreamRequestBody`; multipart parts above 16 MiB spool to `TMPDIR`. Uploads have no storage quota. Verify failed requests leave no spool parts behind.
- **Account roles and host settings.** `account/domain.User.Role` is `admin` or `user`; migration 047 defaults old accounts to `user` and promotes the configured owner email. Registration applies `ADMIN_EMAIL` (default `farismunir2@gmail.com`). Keep host-wide writes behind backend admin middleware; user-owned provider and integration records stay owner-scoped. Shared DB availability comes from the provisioner with request context, including the `POSTGRES_ADMIN_URL` fallback.
- **Task pins (migration 048).** Nullable `tasks.pinned_at` travels through task scans and the list DTO. Authenticated, same-origin `PUT`/`DELETE /api/tasks/:id/pin` writes must scope by task ID and owner, return 404 for unknown or other-user tasks, and be idempotent. Repeated pin preserves its timestamp and list order.
- **Task archive and deletion (migration 051).** `tasks.archived_at` is nullable. Standard lists, needs-input counts, and the 200-task list exclude archived tasks; use the archived query for Archive. Batch transitions are authenticated `POST /api/tasks/archive`, `/restore`, and `/delete` with `{ids:[...]}` and per-id results. Keep them idempotent and report partial failures. Cleanup order for permanent deletion is: stop a running task, remove screenshots, remove `project-notes/tasks/<id>/`, delete task rows, then rebuild that project's notes index. Shared `uploads/` files are not task-owned and must remain. `DeleteAll` must fetch all tasks with `unlimited` before cleaning; using the regular 200-row list leaves files behind. Bound SQL deletes in chunks rather than building one unbounded `IN` clause.
- **Saved roles go stale.** Anything a built-in role needs to work (access groups, its playbook) must be applied on read, not only when the person saves: `Team.WithBuiltIns` overlays access and skill. A prompt-only rule is not enough for behavior that must happen (the Planner asking), so keep it in the embedded skill and check it with a real task.
- **Vendored skills.** Skill files copied from other projects (Designer) stay byte-identical with their `LICENSE` beside them and a line in `skills/designer/NOTICE.md`; check the licence before adding one. Many catalogue entries (Open Design `design-review`, `ui-skills`) are only pointers to another repo with no workflow in them, so read the file before choosing it. Fetch with `curl`: WebFetch only summarizes.
- **Anything from the web is untrusted.** Web text only reaches roles that cannot write or run (`withoutWebWhenItCanChange`), and downloads are limited to pictures a licensed search just offered. Do not add a tool that lets a role fetch an arbitrary address and then act on it.
- **Lint limits shape new code.** `cyclop` package average 5 and `gocyclo` 10 apply to tests too: split big tests into small ones with helpers and move long fixtures to `testdata/`. Make `fieldalignment` happy with `go run golang.org/x/tools/go/analysis/passes/fieldalignment/cmd/fieldalignment@latest -fix <pkgs>`, then check that it kept the comments.
- **Go's HTTP/2 is refused by Flickr's CDN.** Every Go HTTP/2 request to `live.staticflickr.com` gets 429 "CIDR range blocked"; HTTP/1.1 from the same host gets the picture (curl worked, which hid it). `fetch.NewClient` is HTTP/1.1 only for that reason. Unit tests with fake servers cannot catch this: run `BLACKBOX_LIVE=1 go test ./internal/bootstrap -run Live` (real SearXNG, Openverse, Commons, internet; model scripted) after touching `modules/web`.
- **The Designer cannot fetch templates.** Anything it should know from the internet (Nuxt UI templates, icon sets) must be baked into the sandbox image or written into a skill. The sandbox has no network beyond registries, so do not tell a role to clone or scaffold from GitHub (`npm create nuxt -t ui/<name>` downloads from GitHub).
- **Own-plan sign-in (Claude, ChatGPT).** The vendor's CLI is run unmodified in the sandbox image (`claude`, `codex` pinned in `sandbox/Dockerfile`); the app never reads, stores or proxies subscription tokens (Anthropic forbids it; see `implementation-notes.md`). Only the per-person folder `DATA_DIR/cli/<userID>` is mounted at `/home/cli`. A task runs on a plan when its `provider_id` is `plan:claude` or `plan:chatgpt` (`task/domain/plan.go`), which the default-model preference can hold, so no schema column marks it; the sign-in lives in Settings, Models (`PlanProviders.svelte`) and the signed-in plans are options of the default-model picker (value `plan:<program>::default`); `modules/cliagent` owns sign-in, `task/application/cli.go` the turn, `task/adapter/clistream` the output parsers. Do not add models for plans: the program picks its own, and models are never hard-coded.
- **A Unix socket path is limited to about 100 bytes.** `egressproxy.Hub.Dir` fails with a long data folder (a scratchpad path was enough). `Engine.Slot` used to swallow that and the sandbox simply had no network; it now fails when hosts were asked for. Use a short `DATA_DIR` (such as `/tmp/wsbb`) for throwaway instances.
- **Black-box a change by running the binary.** Build `./cmd/workspace`, start it on a spare port with a temporary `DATA_DIR`, register through `/api/auth/register` (send `Origin` equal to `PUBLIC_URL`) and call the HTTP API; leave real data and port 8081 alone. Sign-in cannot be completed without a real account, so the signed-in task path needs the owner's login.
- **Project Env and database settings (migrations 043–049).** `modules/env` owns
  sealed `project_env_vars`; `modules/dbconn` owns the one sealed connection in
  `project_db_connections`. Routes are `/api/projects/:id/env` (GET/PUT),
  `/env/:name` (DELETE), and `/db` (GET/PUT/DELETE) plus `/db/test` (POST).
  Names are uppercase identifiers up to 64 chars; reject `PATH`, `HOME`, all
  proxy names, `LD_*`, `GO*` and `DOCKER_*`; cap at 50 entries and user-written
  values at 4 KiB. Server-managed secrets may be up to 16 KiB for PEM values.
  `runner.WithProjectEnv` and `site.Runtime.WithProjectEnv` inject only that
  project's values after the fixed base env; `bootstrap/taskcli.go` does the
  same for CLI runs. Keep values out of logs and model text. DB probes use
  `egress.PrivateAllowed` at dial time (Mongo checks every resolved address),
  block the server's own port, and are limited to 5/user/minute with a 10 s
  deadline. They run in the app process; sandbox containers stay offline.
  The only database path from a sandbox is the exact-target tunnel (`dbconn/application/tunnel.go`, `egressproxy`, `platform/sandbox/tunnel.go`): never connect a sandbox to a Docker network, and never widen the gate to "a URL that points at the shared host" because users write their own Env. The model gateway follows the same rule: a project reaches it only through the server-side choice in `project_gateway` (owner, provider and address re-checked per run), never because Env holds a matching `OPENAI_BASE_URL`.
  Shared PostgreSQL settings live in `shared_database_settings`, encrypted
  with `platform/secretbox`; `bootstrap/dbconn.go` resolves saved settings at
  provision time and falls back to `POSTGRES_ADMIN_URL` only when none exist.
  `modules/dbconn/adapter/provision` derives schema and role `p_<hash24>` from
  the first 24 hex characters of SHA-256(project ID), and uses `pgx.Identifier`
  for every identifier. In one admin transaction it creates/reconciles the
  restricted login role, creates or verifies schema ownership, revokes `PUBLIC`
  on schema `public`, grants the project role database `CONNECT`, then sets
  `search_path`. PostgreSQL keeps database `TEMPORARY` for `PUBLIC`; do not
  describe the effective database rights as CONNECT-only.
  Shared PostgreSQL settings seal CA, client certificate and key in
  `shared_database_settings`; admin GET returns set flags only. The provisioner
  applies pgx TLS configuration in memory, including explicit fallback order.
  Managed projects receive only the public CA as `DATABASE_SSL_CA`; the URL
  carries the selected `sslmode`. Administrator client certificates and keys
  stay in the server provisioner. Mutual TLS for project apps is unsupported;
  an app that needs its own client certificate must set its own Env values.
  Provision/re-provision and detach remove stale managed `DATABASE_SSL_CERT`
  and `DATABASE_SSL_KEY` values. Detach removes the managed URL for the
  selected kind (`DATABASE_URL` or `MONGODB_URL`) only when a managed
  connection exists. Manual project DB
  writes now return `manual_connection_removed`; saved legacy records remain
  visible and detachable. Detach never invokes the provisioner or drops
  external data. Projects choose SQLite, PostgreSQL, MySQL or MongoDB; the web
  still calls `/db/test` for a saved connection, so retain the probe adapters
  and tests. `POST /db/provision` takes an optional `kind`; an empty body means
  PostgreSQL for old callers. `GET /db` returns `choice` and keeps legacy
  metadata read-only. `/api/databases/kinds` includes configured flags and an
  admin flag. SQL kinds use `DATABASE_URL`; MongoDB uses `MONGODB_URL`.
  MySQL project users are granted only on their generated database. MongoDB
  users get `readWrite` on their own database, with that database as authSource.
  Provision, Save, Delete and DetachSQLite share one per-project lock;
  compensation uses an independent 10-second context and reports
  `compensation_failed` if restoration fails.
  The revoke affects the whole database, so deployments must dedicate it.
  Admin errors collapse to safe categories including `kind_not_configured`,
  `admin_url_invalid`, `admin_rejected`, `insufficient_privileges` and
  `provision_failed`; require a database name in the admin URL path. Never
  expose driver details. Unmanaged `DATABASE_URL` or `MONGODB_URL` blocks
  provisioning when no managed connection exists (`env_name_in_use`).
  The service snapshots all managed Env values and the old sealed password
  before rotating or switching kinds. If local persistence fails, it restores
  both; it never drops a schema, database or user. `PG_ADMIN_TEST_URL` enables the
  optional integration test; it skips when unset and must point to a disposable
  dedicated test database. Connection tests are limited to five per user per
  minute; shared provisioning has a separate limit of ten per user per minute.
# Agent screenshot sessions

- `screenshot_session` is a distinct `coding:exec` tool switch, off by default. Its `RiskMedium` behavior uses the existing action approval path; `screenshot` access does not grant session mutation.
- Resolve session identity only from runner scope plus the current site container. Cookie jars remain in the in-memory `site/adapter/agentsession` registry; reset revokes the current user's task jar, while logout resets the current exact scope even when the app operation fails.
- Login inputs are references to secret Project Env names. Resolve them through the Env use case with project-owner checks and `IsSecret`; pass the resulting JSON only as `sandbox.Spec.Stdin`. Never add values to argv, command transcripts, logs, result text or screenshots.
- The CDP session script uses DOM query/focus and Input insert/key/mouse commands. It may fill only email/text and password inputs, then click a selected submit control. This supports hidden-CSRF form submission and page-owned JSON `onSubmit`, without `Runtime.evaluate` or arbitrary requests.
- A caller-selected readiness selector is the only success signal. Logout clears local cookies after any attempt; the tool cannot prove server-side revocation. Reset stays available when the site is stopped and does not claim to revoke server state.
- `sandbox/capture/testdata/session_fixture.py` plus `session_capture_test.go` cover the cookie/CSRF form, JSON submit handler and two protected desktop/mobile routes when `SANDBOX_TEST_IMAGE` is set. Unit tests cover session scope/expiry/serialization, but neither fixture nor source review proves live Pukat or Next.js hydration.
- Capture descriptions remove query strings and common token/password/CSRF markers and report the main document HTTP status. The PNG itself still reflects the test page; use accounts with safe-to-display data.

## External MCP work contract

- An owner can start a separate orchestrator conversation from an external task.
  `tasks.linked_task_id` is unique and nullable; the linked task stores
  `origin_task_id`, while its `source` and `work_id` remain empty so it has only
  normal internal-task behavior. The SQLite creation transaction commits the
  link, initial request event and transcript together. Later messages use the
  existing `FollowUp` rules; direct external-task follow-up remains rejected.
- The external chat route is `POST /api/tasks/:id/chat` with `{text}` and returns
  `{linkedTaskId}`. It uses authenticated same-origin routing and validates
  owner, project, archived state and linked-task attribution. Context labels
  external timeline claims as reported by the external assistant and keeps
  server-run evidence separate. The report is delimiter-wrapped as data, capped
  to the latest 60 events and 500 characters per event line; evidence shows only
  the server-recorded command name and exit code. External updates never queue an
  agent. Archiving the linked chat lets the next external-task message create a
  fresh linked chat; deleting either task clears the other task's nullable link.

- The eight lifecycle tools (`begin_work`, `set_role`, `update_plan`, `save_research`, `save_requirements`, `report_progress`, `complete_work`, `get_work_state`) use `coding:read` and follow the existing `log_message` switch. They never enable file writing or command execution. A role is attribution only.
- `begin_work` accepts `project?`, `summary`, `idempotency_key?` (8–64 chars), `planned_roles?`; returns task/work IDs, available roles, resumed flag, revision, state and warnings. A same-key, same-request retry returns the same work; changed content rejects the key.
- `set_role` accepts `work_id`, `project?`, `role`, `brief?`; returns the selected role, revision, state and changed flag. `update_plan` accepts `work_id`, `project?`, `base_revision`, `request_id?`, `steps[]`; returns stable step IDs and plan revision. Same request IDs replay the saved response; changed requests reject key reuse.
- `save_research` accepts `work_id`, `project?`, `markdown`, `sources?`, appends a research round and returns saved/path/revision/state. `save_requirements` accepts `work_id`, `project?`, `markdown`, replaces the PRD and returns the same shape. `report_progress` accepts `work_id`, `project?`, `message`, `claims?`, and records claims as self-reported evidence.
- `complete_work` accepts `work_id`, `project?`, `outcome` (`completed`, `failed`, `blocked`), `summary`, `claims?`; returns state, task status and derived evidence. `get_work_state` accepts `work_id`, `project?`; returns current state, plan, progress, document previews, evidence counts and stale flag.
- Ownership mismatch (user, client or project), unknown IDs, and missing tasks all return the unknown-work error. Other errors include closed work, bad role/input, stale revision, changed idempotency key, oversized content, rate limit and open-work cap. Inputs are bounded: summary 4,000 chars; markdown 12,000; role brief 300; 10 planned roles; 40 plan steps (title 200, detail 1,000); 30 sources of 2,048 chars; progress 2,000; 10 claims of 300 chars; 2,000 events. Caps are 20 open works/user and 10/project; begin is 10/minute/user and other lifecycle calls 120/minute/user. Rate buckets are process-local.
- Mutations use revision compare-and-swap. A stale plan returns the current plan plus conflict; role, document and completion writes cannot silently overwrite a newer revision. Event and task updates are atomic. Terminal states (completed, failed, stopped, abandoned) bypass the event limit; ordinary append calls remain capped. MCP call retries use a call ID to replay the already committed event, so Changes retains one Undo record.
- `log_message` writes directly through the legacy thread port or explicit work-call port before returning `saved`; preserve user/request and assistant/message event kinds through both adapters. A failed update to a running work-call event must return an MCP error so the timeline cannot silently stay stale.
- Task events have a stable display `seq` and a task-local change `version`. New writes and in-place updates advance `version`; API/SSE cursors use it, while rendering stays sorted by `seq`. Keep `EventsChangedAfter` available through the `Observe` event decorator, and notify both task and user topics after committed work changes/begins.
- Evidence is `claimed` (client says it happened), `observed` (server saw file paths change), or `ran` (server captured a real exit code). “Proven to work” requires a server-run command with exit code 0 after the latest file change; it does not certify correctness. Status mapping is open→working, blocked→needs-input, completed→done, and failed/stopped/abandoned→failed. Thirty idle minutes marks explicit work stale. Legacy calls without `work_id` retain their existing 30-minute grouping.
- `Stop` closes work but cannot cancel an already running command. MCP `instructions` are guidance: no server observation proves a client called any lifecycle tool, saved the conversation, or disclosed its private reasoning. External work events use `EventRole`, never `EventHandoff`.
