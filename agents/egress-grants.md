# Egress grants (per-task outbound HTTPS approvals)

Design and status of `internal/modules/egressgrant`. Agent-only. Read before touching `platform/egressproxy`, `bootstrap/reach.go`, or the grant tool/endpoints.

**Status: stages 1–6 implemented and verified; the Docker verification gate passed on a hosted runner (Fast #40296058816). Live marimo-pair compatibility is DEFERRED because no notebook/login fixture is available, not PASS. This deferral does not block releasing the app with `EGRESS_GRANTS=false` or a separately approved limited non-marimo canary. It still blocks removing the static marimo allowlist. Production activation requires explicit authorization and the applicable safety checks below.**

## Decisions (user, 2026-10-26)

- Approvers: the project owner and admins, through the UI only. An agent may request, never approve, deny or revoke.
- Default lifetime 24 hours, hard cap 7 days; expiry is automatic.
- Scope is one task in one project (`project_id` + `task_id`), never global and never the whole workspace.
- The static `SANDBOX_EGRESS_HOSTS` list is unchanged and always applies. Grants only add to it.

## Security requirements and how each is met

1. **Internal targets and external grants never share a path.** `Hub.Dir(ctx, id, extra...)` takes strings, and a `host:port` string there becomes an exact target (private addresses, any port). Grants must NOT travel through it. They live in a separate typed registry (`egressproxy.Grants`) consulted by the proxy, and the proxy dials them only through `p.dial` (PublicOnly, port 443). A grant host is never added to `targets`, and `Granted.Targets` never receives one.
2. **Identity is bound server-side.** A sandbox only ever sees the socket folder the server mounts for it. The grant scope (`project_id`, `task_id`) is captured in the listener's closure when the server creates the socket, never read from the request (`Host` header, headers, env, path). One socket per (project, task) that holds grants; two concurrent tasks never share a socket, so one task's grant cannot be used from another's. The model/agent cannot create sockets or choose a scope. Tests: two tasks of one project, same host, only the approved one connects.
3. **Revocation and expiry are enforced in the proxy, not only on read.**
   - The registry holds `grantID -> {host, expiresAt}` in memory, set by the application when a grant is approved and removed when it is revoked or expires (timer at `expiresAt`, plus a check of `now < expiresAt` on every `CONNECT`).
   - Each live tunnel is registered under its grant id; revoke/expiry closes both ends. As a backstop, both connections get a deadline at `expiresAt`.
   - The database is the source of truth. The registry is rebuilt from approved, unexpired rows at startup; a lost registry fails closed (no access).
4. **Hostname and DNS.**
   - One normalizer (`domain.NormalizeHost`) is used when a grant is created and again by the proxy on every `CONNECT`, and the proxy compares the normalized form exactly: lower case, one trailing dot removed, IDNA (Lookup profile) to ASCII, no wildcard, no userinfo/port/path, no IP literal in any notation (dotted, decimal, hex, octal, IPv6, brackets, zone), no single-label or internal-looking names (`localhost`, `.local`, `.internal`, `.lan`, `.home.arpa`, `.localdomain`).
   - At connect time the proxy resolves the name itself, refuses it when ANY answer is non-public (rebinding with mixed answers), and dials the validated IP literal, so the name is not resolved a second time. The existing `egress.Check` `Control` callback stays as defence in depth. IPv4-mapped IPv6 is unmapped before the check (already in `egress.Check`).
   - A CNAME is followed by the resolver; only the final addresses matter and the grant stays for the name that was asked.
5. **No privilege escalation.** Approve/deny/revoke are methods that take a `Decider` built only by the HTTP adapter from the authenticated session. The agent tool path builds `Actor{Kind: Agent}` and can call `Request` only. The sandbox has no network except the proxy, and the proxy refuses the server's own port. No approval credential exists in env, files or tool results. A test fails if any tool/bridge handler can reach an approve/revoke method.
6. **Off by default.** `EGRESS_GRANTS` (read in `platform/config`) gates everything: tool not registered, endpoints 404, registry nil, `reach` returns no hosts. Enabling it before the gate is complete is a bug.
7. **Replay.** A grant id is bound to its task; approving a second time, approving a denied/revoked/expired request, or re-using a stale id after revoke returns an error. An approval for host A never covers host B.
8. **HTTPS-only is not TLS.** The proxy enforces `CONNECT` to port 443 and nothing more: after `200 Connection Established` the bytes are opaque, so a client could speak plaintext, or TLS with another SNI to the same IP (fronting). For grants the proxy therefore reads the first record, requires a TLS ClientHello and requires its SNI to equal the granted host, then forwards the bytes unchanged. It is not a TLS-terminating proxy and never sees content. A client using ECH is refused (fail closed). The static registry list is not changed by this (regression risk), and the docs must say so.

## Stage 2 facts (what the code guarantees)

- **Deciding rights.** `domain.Decider{ID, ProjectID, Owner, Admin}`: `Owner` counts only for `ProjectID == grant.ProjectID`; `Admin` spans projects. The HTTP adapter (stage 6) must build it from the session and from a server-side project-owner lookup, never from request fields.
- **Atomicity.** `Create` is one `INSERT ... SELECT` that checks in the same statement that the task belongs to the project and that the task has no live (pending or unexpired approved) grant for the host. `Decide` runs in one transaction whose first statement is a no-op `UPDATE` that takes SQLite's write lock before anything is read (a read-then-write transaction fails with a stale snapshot when another decision commits in between, which showed up as non-domain errors in CI); then it reads, applies the domain rule and the `UPDATE` names the old status, end, project and task, so a decision made from a stale state changes nothing; it is retried (up to 5 times) and the retry meets the domain rule (`ErrNotPending`/`ErrNotApproved`). Only lock conflicts are retried; any other database error surfaces as itself. Tested with 20-30 goroutines under `-race`.
- **Scope.** `Active` joins `tasks` on both ids, filters `status = 'approved' AND expires_at > now`, and the service re-applies `Grant.Covers` to what the store returned.
- **Not done on purpose:** no cap on pending requests per task (add one if agents flood the UI), no event/log write on decisions (stage 6), no registry or proxy hook (stage 3).
- **Rollback caveat.** Once the app has run with migration 052, an older binary refuses to start (`ErrMigrationMissing`). Roll back by deploying a build that still contains `052_egress_grants.sql`; never delete the file.
- **Two 051 files.** `051_project_gateway.sql` and `051_task_archived_at.sql` are both applied on real databases. The runner journals by full file name and sorts names, so it is safe. `test/go/platform/database/migrate_test.go` checks migration journal integrity. Never rename or renumber either file.

## Stage 3 must also prove (proxy gate)

A valid ClientHello with the right SNI does not prove that everything inside the tunnel is TLS: after the first record the proxy still forwards opaque bytes, and a client can finish a handshake and then send anything, or put plaintext after a ClientHello. The proxy cannot see inside without terminating TLS, which this design does not do. So stage 3 states the limit in its docs, and tests at least: plaintext first bytes refused, a non-ClientHello record refused, SNI different from the granted host refused, no SNI refused, ECH-style outer SNI refused, a truncated or oversized first record refused with a timeout, and a ClientHello followed by plaintext still reaches only the approved public address (the limit: the destination, not the content, is what is enforced). These tests must exist before the activation gate.

## Stage 3 facts (proxy enforcement, in `platform/egressproxy`)

- **Three separate paths, one switch.** `Proxy.ServeHTTP` tries the older rules first, unchanged: registry list and exact targets (`tunnelTo`). Only when none allows the request and the proxy belongs to a task socket (`task.grants != nil`) does it call `serveGrant` (`grantpath.go`). A proxy from `Hub.Dir` has no grants, so its behaviour is byte-for-byte the old one (the old tests pass untouched). A grant host is never written to `Proxy.hosts` or `Proxy.targets` (tested), and `Hub.TaskDir`'s `extra` hosts keep going through `WithHosts` exactly as in `Dir`.
- **Identity.** `Hub.TaskDir(ctx, workspaceID, Scope{Project, Task}, extra...)` makes one socket and folder per scope. The scope is captured in the listener's proxy when the server creates it (`proxy.task.scope`); nothing in a request (`Host`, headers, path) can change it, and a sandbox is only mounted its own folder. Zero or half scopes are refused (`ErrBadGrant`) and `Lease` also refuses them. `Hub.Remove(workspaceID)` stops task sockets too; `RemoveTask(scope)` stops one task's and revokes its grants.
- **Registry.** `Grants` (`grants.go`, `lease.go`, `limits.go`): `Allow(id, scope, host, ends)` (host canonicalized by `egress.CanonicalHost`, a timer revokes at `ends`), `Revoke(id)`, `Clear(scope)`, `Close()`. `Lease(scope, host)` checks the grant, the end time, and the per-task/total limits and registers the tunnel in ONE locked step, so a revoke either sees the tunnel and closes it or the tunnel never opens (tested with 16 goroutines racing a revoke). Every connection of a tunnel (client, destination) is added to its `Lease`; `Revoke` closes them all before it returns. Closing a lease takes the registry lock again, so never close leases while holding it (`Allow` once deadlocked on that).
- **Fail closed.** Unknown, expired, revoked, over-limit, zero scope, non-canonical host, port other than 443, a failing `Verifier`, a name that does not resolve, a name with ANY non-public answer: all refuse (403, or 502 when nothing resolves, 503 over the limit). The proxy holds grants only in memory: a restart or a lost registry means no access. `Verifier` (stage 4 will back it with the database) is asked on every CONNECT after the local match; an error refuses the connection. After a database error stage 4 should also call `Grants.Close`/`Clear`.
- **DNS and destination pinning.** The name is resolved once (`lookupIP`), every answer must pass `egress.Check` PublicOnly (IPv4-mapped IPv6 unmapped; reserved, NAT64, 6to4, link-local, private and loopback refused), and the connection goes to the checked IP literal, so a second lookup can never lead elsewhere. The dialer's `Control` check stays as defence in depth. A CNAME is followed by the resolver; only final addresses matter.
- **TLS check, and its limit.** After `200 Connection Established` the proxy reads exactly one TLS record (`clienthello.go`): handshake record, version 3.1-3.3, at most 16384 bytes, one unfragmented ClientHello with exact lengths, no repeated extension, no `encrypted_client_hello`, exactly one `host_name` whose canonical form equals the granted host. Anything else closes the tunnel before the destination sees a byte. Then bytes are forwarded unchanged. **This proves the destination name, not that the rest of the tunnel is TLS**: after the hello the client can send anything to that approved host (the proxy never terminates TLS and never sees content). The docs for people must say this. Tests: plaintext, SSH, garbage, alert and application-data records, bad versions and lengths, truncation, trailing bytes, fragmentation, duplicate/ECH/multiple/non-host names, IP and wildcard names, no SNI, mismatched SNI, a fuzz target.
- **Resource limits** (`Limits`, defaults 16 per task, 128 total): the hello must arrive within `Handshake` (10 s) of the tunnel opening, `Idle` (5 min) closes a quiet tunnel (deadline refreshed on each read and write), `Dial` (10 s) bounds resolution plus connect, and every deadline is capped at the grant's end.
- **Host spelling.** `egress.CanonicalHost` (platform) and `domain.NormalizeHost` (module) cannot import each other, so `test/go/app/egress/egress_host_test.go` asserts that for every name the domain accepts the proxy yields the same spelling. Keep that test when changing either.

## Residual risks (state them in the review)

- The feature is wired but disabled by default. Docker black-box Subpath tests passed on hosted CI; real marimo compatibility is deferred. A core app release with grants off is separate from a limited grants canary and from the later marimo static-allowlist migration.
- Content to an approved host cannot be inspected; approving a host trusts its operator and its DNS (an attacker who controls the approved name's DNS chooses which public address answers).
- ECH and a ClientHello split over several records are refused, so some clients will not work through a grant.
- Expiry and revoke are enforced in-process; a crash drops all grants (fail closed) but also all tunnels.
- No per-destination rate limit and no bandwidth cap beyond the connection limits.
- The static `SANDBOX_EGRESS_HOSTS` list still contains the marimo host for everyone until grants are enabled (see above).

## Stage 4 facts (runtime integration)

- **Flag.** `EGRESS_GRANTS` (`config.Config.EgressGrants`, `strconv.ParseBool`, anything unreadable is false). Compose files pass it through with default `false`. Off: `newSandboxEngine` does not call `startEgressGrants`, the hub keeps no registry (`Hub.Enabled()` false), `runner.Engine.socket` returns the workspace socket exactly as before whatever the context carries, and migrations 052 and 053 are the only traces. `test/go/modules/egressgrant/runtime/grants_test.go` checks the disabled state.
- **Where the scope comes from.** `agentTools.Execute` wraps the context with `runner.WithTask(ctx, scope.ProjectID, scope.TaskID)`; `scope` is the `ToolScope` the task loop builds from its own task row (`task/application/calls.go`), never from the model's tool input. `Runner.bind` distrusts a scope whose project is not the runner's own project (or is empty) and the command then gets no socket. `Engine.socket` additionally asks `Extras.Scopes.TaskLive` (the egressgrant service) before it calls `Hub.TaskDir`. With grants on and a scope present the command gets the task's socket or no socket: never the workspace socket in its place (a workspace socket carries no grants, so that would not widen access, but it would hide a failure). Without a scope in the context (plan CLIs via `Engine.Lease`, `Slot`, sites, checks started from the UI) the workspace socket is used as before and no grants apply.
- **Filesystem and mount isolation** (`test/go/modules/runner/sandbox_test.go`, needs `SANDBOX_TEST_IMAGE`, run against the local toolbox image): a real container checks workspace write confinement, network access and privileges. Task-scoped grant routing through real proxy sockets is checked in `test/go/modules/egressgrant/runtime/grants_test.go`. The volume `Subpath` form is covered by `test/go/platform/sandbox/subpath_integration_test.go`.
- **Database is the source of truth, the registry a mirror.** `Service.syncGrant` runs after every committed decision, under one mutex that also guards `Reconcile`; it re-reads the grant and the task and then allows or revokes in the registry, so racing commits cannot leave an older state behind (tested with concurrent approve/revoke/sweep rounds under `-race`). A failure ends the grant in the registry and the decision call returns the error.
- **Verifier.** `egressVerifier` calls `Service.Verify` (5 s timeout) on every CONNECT that matched a grant: the grant row must cover project, task and host, be approved and unexpired, and the task must be live. Database error, missing service, wrong scope, ended task: refused.
- **Task liveness.** A task is live when it exists in that project, is not archived and is not `done` or `failed` (`review` and `needs-input` count as live). `Store.EndInactive` ends the pending and approved grants of tasks that are not live for good (`revoked` or `denied`, `decided_by = 'system:task-ended'`); a task that comes back to life does not get them back. A deleted task's rows go with it (cascade).
- **Restart.** `startEgressGrants` calls the same `Reconcile` that the 5 s sweep runs. It restores exactly the approved, unexpired grants of live tasks, nothing else. If the database cannot be read the registry is emptied (`Reconcile` revokes everything) and rebuilt by the next good sweep.
- **Sweep and lag.** Revoke and approve act on the registry before the call returns. A task that ends, is archived or deleted loses its grants and open tunnels within one sweep (5 s); new connections are refused at once by the verifier. The sweep also stops the sockets of tasks that are no longer live (`Hub.RemoveTask`).
- **One instance only.** The registry is in memory and tunnels live in this process. `startEgressGrants` takes an exclusive `flock` on `DATA_DIR/egress/.grants.lock`; a second process on the same data folder fails to get it, logs "egress grants stay off", and runs without grants (its hub has no registry, so it serves none). That is the supported answer to "several instances": grants work in exactly one. Two processes on different hosts sharing a database over a network file system are not detected (flock is per host) and are not supported; because every revoke and approve is also written to the database and the verifier reads it, a second process that somehow ran grants would still refuse new connections after a revoke, but could keep an old tunnel until its own sweep (5 s). No distributed registry is planned.
- **Superseded in stage 5:** vendor programs now get task sockets (below). `Slot` (sign-in and model lists, no task) and sites still use the workspace socket.

## Stage 5 facts

- **Vendor programs (Claude Code, Codex).** `taskapp.CLIRequest` has a `TaskID`, filled from the task row by `cli.go` and `planworker.go` (a teammate's `domain.Task` is the same row). `plans.prepareRun` puts `runner.WithTask(ctx, req.ProjectID, req.TaskID)` on the context, so `Engine.Lease` gives the program's container that task's socket. `Engine.prepare` refuses to start the program when a scope cannot be confirmed. `Slot` and `SiteSpec` ignore scope, so a site or sign-in container never gets grants. `test/go/modules/runner/reach_test.go` covers vendor host reach, and `test/go/modules/egressgrant/runtime/grants_test.go` covers task-scoped proxy routing.
- **`request_egress(host, reason)`** (`bootstrap/agenttools_egress.go`, `coding/domain/egress_tool.go`). Offered only when grants run (`agentTools.egress != nil`); not in `codingdomain.Tools()`, so outside AI apps never see it; it follows the `run_command` switch (`SwitchOf`, `toolGate`). Project and task come from `ToolScope`; arguments named `project_id`, `task_id` or `status` are ignored. The actor is always `Actor{Agent, "agent:<task>"}` and the tool only calls `Service.Ask`, which can create or return a request; nothing in the tool path can approve, deny or revoke. Teammates on a plan get it through the MCP bridge when their role may run commands (`roleToolSet` adds it to `run_command` roles; `siteToolNames`). Solo plan tasks (no team, no bridge) cannot call it; a person-made request (stage 6) covers them.
- **Idempotency and limits.** `Service.Ask` returns the live request for the same host (any spelling) instead of an error, also while approved. One `INSERT ... SELECT` enforces: open task of the project, no live request for the host, at most 5 pending per task, at most 10 requests by an agent per task per hour (`application.DefaultLimits`; browser request and decision endpoints additionally have a per-user rate limit of 30 per minute). Tested with 12 sequential and 30 concurrent callers.
- **Task end is immediate.** `egressTasks` wraps the task store at the composition root (only when grants run): `SetStatus` to done or failed, `Archive`, `DeleteOwned`, `DeleteProject` and `DeleteAll` call `egressRuntime.TaskEnded`, which ends the task's pending and approved grants in the database for good, clears them from the registry (`Grants.ClearTask`, which closes every tunnel before it returns) and stops the task's sockets. Statuses review and needs-input do not end anything. The 5 s sweep is only the safety net. A task retried after failing needs its hosts approved again.
- **Database failure stays fail-closed.** Unchanged: the verifier refuses when the database cannot answer, a sweep that cannot read it empties the registry, `TaskEnded` clears the registry even when the database write fails and reports the error.

## Stage 6 facts (implemented, activation still prohibited)

- **HTTP and identity.** Browser routes under `/api/projects/:id/egress-grants` are mounted only with a running grant registry. Every request verifies session identity, current account role and active project ownership. A grant from another project is not returned. Agent tools have no approval endpoint, bearer token or CSRF secret. Manual task IDs are checked against the project's live tasks in SQLite, not trusted from JSON.
- **CSRF and rate limit.** Mutations require the existing origin guard plus `X-Egress-CSRF`, a constant-time checked HMAC over the authenticated user and their session cookie under an ephemeral server key. The header is mandatory even without an Origin header. There are 30 mutations per user per minute; the existing five-pending-per-task limit also applies. Restart invalidates CSRF tokens, which the browser retrieves again for each mutation.
- **Atomic decisions.** SQLite checks task liveness while holding the same write lock as a decision. Concurrent approval, expiry, replay, task end and grant scope changes cannot silently authorize stale work. After a successful commit, proxy synchronization runs before the API responds. Enforcement errors fail closed.
- **Project UI.** The tab appears only when the server exposes grants. It lists pending and earlier decisions, task, hostname, reason, requester, expiry and status. Owner/admin users can request, approve, deny or revoke; people can manually request for active solo tasks. All server-provided fields use escaped Svelte text; no HTML interpretation.
- **Task thread.** Browser-originated requests and decisions append a message through the existing task event store. Agent-originated requests already appear in the tool-action thread. Message delivery failure after a committed decision does not reopen network access or roll back a valid decision.
- **Activity log.** Migration `053_egress_audit.sql` introduced SQLite triggers; the append-only `054_egress_actor_attribution.sql` replaces them with actor-aware versions while preserving `activity.user_id` as the project owner for visibility. The runtime sweep records effective expiry once per grant and failed registry enforcement when the database remains reachable. Audit messages include hostname, grant ID and actor; never the reason, request body or secret. Project-owner visibility is reused.
- **Residual risks.** Database outage prevents writing an enforcement failure to SQLite; the proxy still fails closed. Some denied per-connection checks are refusals rather than individual activity rows. Thread notifications are best effort after commit. HTTP `Ask` detects existing grants and skips duplicate notifications; replayed decisions fail without another notification or activity entry. The proxy's TLS ClientHello limitations and static allowlist remain unchanged. Any rollback after applying migration 053 requires retaining both 052 and 053.
- **Verification.** Unit, HTTP authorization/CSRF/rate/replay, task-liveness, SQLite audit/expiry, concurrency, proxy regression and `make verify` remain mandatory. The Docker verification gate passed Subpath, HTTPS grant and HTTP/container checks (run #40296058816); no need to repeat solely because another sandbox lacks Docker. Real marimo-pair remains DEFERRED until a valid notebook/login fixture exists; this only prevents marimo allowlist removal, not releases with grants off. Activation requires independent review and explicit authorization.
