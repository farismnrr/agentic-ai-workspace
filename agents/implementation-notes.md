# Implementation notes

Detail for agents working on the backend. People read the short versions in `docs/system-design.md`; this file keeps the long, exact ones. Update it in the same task when the code changes.

## Spaces and the coding MCP endpoint

- `modules/space` and `modules/coding`: each space is an MCP endpoint at `/api/<name>`. The first, `coding`, offers tools to list, read, search, change files in, run tasks and commands in, and start the web app of the caller's project for that app.
- Every call resolves the project from the verified token (user id plus the app's name from its grant). `projectapp.ForApp` finds or makes the live project whose `source` is that name, so one person can never name another's files and two apps never share a folder.
- The tool catalogue (`coding/domain.Tools()`) and the switches (`tool_permissions`, `approval_settings`) are the same ones the agent obeys. Paths are confined with Go's `os.Root`, and secret files are never shown.
- Each tool has a scope (`coding:read`, `coding:write`, `coding:exec`) and a switch the person controls. A call must pass the switch, then the token's scope, and is always written to the activity log.
- Edits save the old content first (under `DATA_DIR/backups`); that is what Undo restores.
- Tasks are named commands from `.workspace/tasks.json`, run without a shell, one at a time. The tools can never read or write that folder.

## OAuth discovery from `CONNECTOR_URL/api/coding`

1. A call without a token gets `401` and a pointer to `/.well-known/oauth-protected-resource/api/coding`.
2. That document names the authorization server and the permissions (`coding:read`).
3. `/.well-known/oauth-authorization-server` (and the OpenID Connect twin) lists the endpoints, PKCE `S256`, and the two ways to register: Client ID Metadata Documents and dynamic registration.
4. The app sends the person to `/oauth/authorize`, which opens the consent page in the app. After approval the app exchanges the code at `/oauth/token`.

Tokens are opaque and stored hashed, tied to one space, with rotating refresh tokens. A replayed code or refresh token revokes the whole connection.

## The sandbox

Tasks and commands run inside `platform/sandbox`, which starts one throwaway Docker container per run through the Docker Engine API (the `moby/moby/client` module, so the binary stays static and needs no Docker CLI).

**Image.** `SANDBOX_IMAGE` (default `ghcr.io/<owner>/agentic-ai-workspace-sandbox`, built from `sandbox/Dockerfile`: Python, Node.js, Go, Rust, Java, Maven, the GitHub CLI, Bash and Chromium headless shell for screenshots, pulled on first use). Toolchains live in the image, so every container shares the same read-only layers and nothing is downloaded per person. The image advertises them in the `io.masihawam.toolchains` label, which the agent prompt reads.

**Container.**
- no network interface, read-only root filesystem, private `/tmp` tmpfs, all capabilities dropped, `no-new-privileges`, Docker's default seccomp profile, an init process;
- `memory` (swap off), `cpu`, `pids` and file-size limits;
- runs as the server's own uid and gid, so files stay editable;
- `SANDBOX_RUNTIME` can select a hardened runtime such as gVisor.

**Mounts.** The person's workspace at `/workspace`, their package cache at `/cache` (`DATA_DIR/caches/<id>`, emptied above 5 GiB) and the proxy socket folder read-only at `/run/egress`. They are bind mounts when the server runs on the host, or the data volume narrowed with a volume `Subpath` (Engine API 1.45+) when the server itself runs in a container, so a run can never see another person's folder.

**Network.** Registry access goes through `platform/egressproxy`: an HTTPS `CONNECT` proxy on one Unix socket per workspace (the server still listens on one TCP port). It allows only `SANDBOX_EGRESS_HOSTS` on port 443, with every resolved address checked by `platform/egress` at dial time. A `host:port` entry in a run's extra hosts is an exact target instead (any port, dialed with `PrivateAllowed` and the server's `OwnPort` refused, see `WithOwnPort`); it is how a project reaches its database. The gate is `dbconn/application/tunnel.go` (`Tunnels.Target`): the project's connection is `Managed` and its host:port equals the admin's current saved server for that kind, otherwise no entry. What a project may reach is one `runner.Reach` (built in `bootstrap/reach.go` from `dbconn.Tunnels` and `gateway.Service.Grant`); `Granted{Targets, Env}.Apply` sets `Spec.Tunnels` only when the proxy socket is mounted and returns the env to put in the base before the project's own values (first-wins), so a server variable beats a typed one. The same port is never opened twice: the database keeps it. `platform/sandbox/tunnel.go` adds `ExtraHosts name:127.0.0.1` (so the saved URL and TLS name keep working under `network none`) and `TUNNEL_TARGETS` (space separated), which `sandbox-entry` turns into one `socat` listener per target on the same loopback port through `PROXY:127.0.0.1:host:port,proxyport=3128`. An IP-literal host cannot be aliased, so `localize` rewrites matching URLs to `127.0.0.1`. An outside `TUNNEL_TARGETS` env value is always dropped. The model gateway (`modules/gateway`, table `project_gateway`) is chosen per project by its owner from their own enabled `compatible` providers on this computer; `Grant` re-checks owner, provider and address on every run and injects `OPENAI_BASE_URL` / `OPENAI_API_KEY` per run, never into Variables. Docker writes no `/etc/hosts` when `Config.NetworkDisabled` is true, so `ExtraHosts` would be ignored: `createOptions` leaves that flag off for a run with a tunnel alias (even `localhost` gets one), while `NetworkMode: none` still leaves only loopback. Verified against `shared-postgres`: the saved name answers a Postgres `SSLRequest` from inside, and `shared-redis:6379`, the same host on another port, the app's own port and the internet are all refused. The vendors' CLI programs get the same tunnel through `plans.withDatabase` in `bootstrap/taskcli_env.go` (their hosts plus the exact target, `Spec.Tunnel` set after `Lease`); the `POSTGRES_ADMIN_URL` fallback gets none. Inside the container `sandbox-entry` bridges `127.0.0.1:3128` to that socket and the usual `HTTPS_PROXY` variables point there. `NO_PROXY` lists loopback, so a command can `curl` a server it started on `127.0.0.1`; without it the registry-only proxy answered 403 and the agent could not check its own site.

**Commands.** `run_command` (exec scope, off by default, asks every time) runs `bash -c` in the sandbox. Named tasks run their argument vector directly.

**Lifecycle.**
- Containers carry a label with an owner id derived from the data folder; at startup the server removes only leftovers with its own owner id.
- Docker is opened lazily and warmed in the background. If the daemon is unreachable, checks fail with a plain reason and nothing else breaks.
- A shared pool (`MAX_SANDBOXES`) bounds how many containers run at once. A watcher stops a run whose workspace grows past 2 GiB.

**Not covered.** Disk quotas (the watcher polls once a second, so use filesystem quotas for a hard limit); data smuggled out inside requests to an allowed registry (it has no credentials, but a request can still carry bytes); and the host kernel and Docker daemon, which a container always shares with the host. Whoever controls the Docker socket controls the host, so Docker rootless mode is the recommended mitigation.

Web apps the AI starts (`modules/site`) use the same sandbox with a long-lived container, reached through a Unix socket by a `/run/<project-id>/` proxy on the same port. See `docs/sites.md` for the isolation layers. The app's port is exposed as a Unix socket (`socat`, started by `sandbox-entry` when `SITE_PORT` is set) in `DATA_DIR/sites`, mounted at `/run/site`. Sites live in the `sites` table and reset at startup, because containers do not survive a restart. For a private site the proxy keeps the app's cookies in an in-memory jar (`adapter/http/jar.go`), so a sandboxed page can stay signed in without any browser cookie.

## The agent loop

- There is no separate chat: every message starts a thread in a project (`modules/task`), and the agent decides whether to answer directly or to plan and work.
- Reads run on their own. Edits, deletes, moves, commands and starting a web app wait for a yes unless the person turned on Skip approvals for the space, which never overrides an off switch.
- A tool switched off in Spaces & tools is neither offered to the model nor run (checked again right before each call).
- A run that changed nothing ends as an answer (status Done, no receipt) and the thread stays open.
- The loop sends the conversation to the chosen model, runs tools in the project folder, and records plain-language steps and a provider-neutral transcript. Because the transcript is stored, a task can pause for approval and resume later.
- Proof is built only from checks the server ran after the last change. "How it was tested" only counts them ("Ran 3 checks: 2 passed, 1 failed"); each command is named under "What was checked". Claims the AI makes without running anything are listed as claimed.
- A project's checks live in `.workspace/tasks.json`; only the Checks tab changes them.

## The agent team

`modules/agentteam` holds a person's roles; `modules/task` runs them. Built on the loop above, not beside it.

- **Config.** `agent_roles` (one row per role, keyed `(user_id, key)`) and `agent_teams.use_by_default`. No saved team means the built-in SDLC presets (`agentteam/domain/preset.go`); saving replaces the whole team; reset deletes it. Exactly one lead, at most `MaxRoles` roles. `access` is a list of groups (`read` always, plus `write`, `exec`), turned into tool names in `bootstrap/agentteam.go`; the lead is not limited by it. Built-in roles are the same for everyone and cannot be removed: `Team.WithBuiltIns` adds any missing one back on save and on read (so teams saved before a new built-in role existed get it), and `Role.normalize` forces their preset access. Only the orchestrator leads; a role the person adds never does. Roles live per person (`agent_roles.user_id`), so one person's edits never reach another. `MaxRoles` is 20, counting the 12 built-in.
- **Per task.** `tasks.team` is set at creation: every new task has the team (`chooseTeam`), the person has no switch in the composer or in Settings; only code that starts tasks itself can pass `CreateInput.Team = false`, which the single-agent tests do (`"team":false` in `agentRig.start`). `agent_teams.use_by_default` is no longer read; the column stays because migrations are append-only. A team task with no enabled teammate runs solo. With a team the lead's model is the composer's pick, else the lead role's, else the default.
- **The lead never changes anything.** On a team task the lead's runner (`Runner.leads`) is not offered any tool whose risk is not none (edit, write, delete, move, run a task or command, start or stop a site) and refuses it if called (`refusal`). A first test with a real model showed prompts alone are ignored: the lead said "medium, I will ask the Planner" and then wrote every file itself. Reads stay. A small job goes straight to the Developer. If no teammate can edit files, the lead is told to ask the person to turn on the Developer (`canChange`). Solo tasks and teammates are unchanged. If a real model still skips the Planner on a medium job, the next guard is to refuse delegating to a role that can change files until a PRD exists.
- **Delegation.** The lead gets a `delegate{role, brief, context}` tool and runs the teammate inside the same run (`delegate.go`): a second `Runner` (`teamrunner.go`) with its own transcript, a tool gate narrowed to the role, and every event labelled `Agent`. One level only: teammates get `report`, never `delegate`, `update_plan` or `finish`, and `ask_user` only with the `ask` access group. Hallucinated loop tools are refused in `handle`.
- **Fonts come from npm (any stack).** The sandbox reaches registries only, so Google Fonts cannot be fetched in a build or a command (a build plugin that downloads fonts, such as Nuxt's, falls back to a system font). The rule is stack-agnostic: Fontsource packages (`@fontsource-variable/<slug>`, family `'<Name> Variable'`; static `@fontsource/<slug>`, one CSS import per weight), imported with a bundler or copied from `node_modules/.../files/*.woff2` with a hand-written `@font-face` for plain HTML. It lives in `developer/delivery-rules` section 7, the Designer's workflow, the solo agent's system prompt (`prompt.go`) and the Nuxt starter (`@fontsource-variable/public-sans`, verified: the build bundles the woff2). `withHint` (`hint.go`) adds the same way forward to a failed tool result that names a font host, and `fontLinkHold` refuses a `write_file`/`edit_file` whose new text links a font host. A live run showed why the playbook alone is not enough: the lead's brief and the PRD asked for the Google link and the Developer followed the brief, so `leadRules` rule 6 now says a brief names a font and never links one. A teammate on a plan writes with its program's own Write tool, which the server cannot inspect, so for it only the brief and the prompt hold. We did not open `fonts.googleapis.com` and `fonts.gstatic.com` in `SANDBOX_EGRESS_HOSTS`: the page in the person's browser can load them (the Sites policy is `sandbox` only), but the build and the screenshots cannot, and a pinned local font needs no third-party request.
- **Only DevOps runs the app (`serverguard.go`, `plansite.go`).** `Role.RunsApps` (preset DevOps only, not saved, not settable on custom roles) decides who gets `start_site` and `stop_site` (`bootstrap/agentteam.go` `toolsFor`); every other role, the Developer included, asks the orchestrator. The DevOps skill `start-the-app` makes `start_site` the only way: it is the sole route to Sites, so the person opens the app from any computer. Guards: (1) `serverHold` refuses a `run_command` that starts a server or leaves a process behind (`nohup`, a trailing `&`, `npm run dev`, `http.server`, `nuxt dev`, `uvicorn`, ...); (2) `localAddressHeld` sends a `finish` whose summary names 127.0.0.1, localhost or 0.0.0.0 back, twice at most; (3) a Designer's report saying "Needs the app started" is not held for not looking. A teammate on a plan has no `start_site` of its own, so `siteBridge` serves `start_site`/`stop_site` to its program over the same MCP bridge as the lead's tools, through `handle` (Security hold, approval, the link in the thread); call ids are `site-<hash(job, name, input)>` so an approval survives the job starting over. A plan program's own Bash cannot be inspected, so for it only the prompt covers the shell-server rule.
- **A stuck teammate asks for help (`stuck.go`).** A teammate's prompt (`childWorkflow`) says that when the same problem beats it twice it calls `report` at once with `Stuck: <tried, exact error, question>` instead of going on until its 60-step share ran out. Backstops on the teammate's own loop: after 3 failed project-tool steps in a row (`runState.misses`, reset by any step that works) a nudge block tells it to report; after 6 the server ends the job as failed with the last error, and every failed job's report to the lead ends with `stuckAdvice`. `leadRules` rule 5 tells the lead to hand the Researcher the exact problem, then send the same teammate the job again with the findings, at most twice per problem. The lead's own loop and a teammate on a plan are not counted (a plan's program runs its own steps); they get the prompt rule only.
- **Transcript scope.** A teammate's blocks live in `task_transcript.scope` (the delegate call id; empty is the lead). `LoadTranscript` reads scope `''` only. `seq` stays shared per task. Compaction and the context meter follow the lead (`saveContext` skips teammates).
- **Pause and resume.** A teammate that needs an approval returns `stopWaiting` through `delegate`; the lead's `delegate` call stays unanswered. After the answer the task is requeued and the same teammate continues from its own transcript. `task_delegations` stores the model chosen at the start, so a resume never changes model. A finished delegation is idempotent: the stored report is replayed as the tool result.
- **Model for a role.** The role's provider and model if the person can reach it, else `Models.Default`, else the task's model. Usage is recorded against that model.
- **Limits.** One `budget` per run, drawn by the lead and every teammate (`TeamSteps` 400, `TeamWallTime` 2 hours). Each delegation also gets `DelegateSteps` 60 per segment; running out fails only that delegation (the lead reads an error result). Running out of the shared budget ends the run with the usual Continue hint.
- **Report and proof.** The result of `delegate` is the teammate's report plus what the server recorded for them (files changed, checks run). Their events sit in the same thread, so `buildProof` and `workDone` count them like any others; their claims never count.
- **Sizing and plans.** Research behind it: Anthropic's multi-agent write-up (sub-agents report only to the lead, effort is scaled by rules in the prompt, 50 sub-agents for a simple query was a real failure, coding is a poor fit, about 15x the tokens), Cognition's "Don't build multi-agents" (share context, parallel agents make conflicting implicit decisions) and Anthropic's "Building effective agents" (simplest thing that works). So: no free chat between teammates, the lead coordinates. `leadRules` (`system.go`) makes it size the request first: question, small (alone, no plan list), medium (Planner, Developer, QA), large (add Researcher/BA/Architect only for what is unknown, then Reviewer); when unsure take the smaller size, but making something new is never small (a first test let the lead call a four-file site "small"), and medium or large work ends with a check run by QA.
- **PRD and questions.** Research: Claude Code's AskUserQuestion (one decision per question, two to four options with the recommended one first, always a free-text "Other"), Codex plan mode's `request_user_input`, Kiro specs (requirements with checkable acceptance criteria) and agent-PRD templates (goals and explicit non-goals matter most). ngodingpakeai.com is only a marketing page, nothing to learn from its flow. The Planner (and Business Analyst) have the `ask` access group, which adds `ask_user` to the teammate's tools (`canAsk`); the question is a normal `EventQuestion` labelled with the teammate, and answering resumes the same teammate like an approval does. A teammate may ask at most 6 questions per task (`askedEnough`, counted per question, not per call). The Planner writes the PRD as the `document` of its `report`; `deliver` saves it as `tasks.prd` (migration 030), appends an `EventPRD`, returns it to the lead, and `briefWithPlan` adds it to every later brief. The lead asks the person once to approve before the build (`leadRules`). Questions are only for what blocks the scope; a sensible default goes under Assumptions.
- **Question form.** `ask_user` takes `{questions:[{header, question, type single|multi|text, options:[{label, description}]}]}`, one to four per call (`askargs.go`); options may be plain strings and the old `{question, options[]}` shape still parses. The event keeps `Questions` and also `Text`/`Options` of the first (old events and tests). The answer is `POST .../answer {answers: string[][]}` (one list of replies per question; `{choice}` still answers a one-question form), checked in `answerform.go` and stored as one summary line in `Answered`, so the transcript result stays "The person answered: ...". The person can always type their own reply, so the agent is told not to add an Other option. An option may carry `preview`, the name of a picture (a plain slug, `previewName` drops anything else); the page shows it on a card and a form with pictures may have up to 8 options (`maxOptions`). The names are the style families of the Designer's library that have a picture; the Planner and Designer skills list them. Web: `QuestionCard` + `QuestionField` (daisyUI radio/checkbox/input), logic in `logic/question-form.ts`.
- **Screenshots.** The `screenshot{path, device, y, overview}` tool (`bootstrap/agenttools_shot.go`, name in `coding/domain/tools.go`, follows the `run_command` switch like the site tools, risk none, offered to every role with read access so a Reviewer can use it) photographs the project's running site. `site.Service.Capture` checks the site runs, then `site/adapter/runtime/capture.go` starts a one-shot container (`Engine.RunOnce`, a place of the pool) that mounts the site's socket folder and runs `node /usr/local/share/capture/capture.ts '<json>'` from `sandbox/capture/`: `sandbox-entry.sh` bridges `/run/site/s.sock` to `127.0.0.1:CAPTURE_PORT` (the app's own port; the proxy strips the path prefix, so the page is `/`), and the script drives `chromium-headless-shell` over a minimal CDP client on Node's built-in WebSocket (no npm package; Node 24 strips the TypeScript types) with `--no-sandbox` (the container has no capabilities or user namespaces; it is the isolation). It prints `CAPTURE_JSON:{...}` with a base64 PNG, the clip and the page facts from `inspect.ts` (sideways overflow, broken images, missing alt, small targets, unlabeled fields, low contrast, headings, console errors, failed requests); `application.ParseCapture` reads it and `domain.Capture.Describe` writes the text the model gets. Sizes: desktop 1280x800, mobile 390x844; the default shot is one screen from `y`, `overview` scales the whole page to at most 1568px on its long edge (a `tool_result` image over the model's limit is rejected, not resized). The container has no internet, so external fonts and images fail there. The PNG goes through `ToolResult.Image`: `Runner.saveShot` stores it (`Shots` port, `adapter/shots`, `DATA_DIR/shots/<task>/<id>.png`), answers the call with a `Block{Image: id}` and appends an `EventShot`; the thread shows it with `ShotCard` from `GET /api/tasks/:id/shots/:name` (owner only, removed with the task in `DeleteAll`). Before each model turn `withImages` fills `Block.Data` for the latest two screenshots only (every image is resent and billed each turn); Anthropic gets the image part before the text inside `tool_result`, Chat Completions a `user` message with `image_url` after the tool messages. No model is named: a request that the model rejects (non-retryable, status 0/400/413/415/422) is repeated once without images and `runState.noImages` keeps the rest of the run on the text report (`askSeeing`). Gotcha: the capture script must flush stdout before it exits (`process.stdout.write` with a callback, then `process.exit`): a plain `console.log` then `process.exit` cut every output at the 64 KiB pipe size, so each desktop screenshot failed with "unreadable result" while the small phone ones worked; the integration test uses a noisy page so the picture is larger than a pipe.
- **Skills and library.** A skill is a playbook of a built-in role: `agentteam/domain/skills/<role>/<skill>/SKILL.md` (frontmatter `name`, `description`, optional `always: true`; embedded with `go:embed`, `SkillsFor`). Skills are not saved or sent to the web: `Role.Skills` and `Role.Library` are filled on read (`WithBuiltIns`, `normalize`). `WithBuiltIns` also forces a built-in role's current `Access` on read, because a team saved before a role gained `ask` kept `access=[read]` and its Planner never got `ask_user` (the likely reason it asked nothing). `childPrompt` puts `always` skills in the prompt (the playbook wins over the role prompt, `appendSkills`) and only lists the others; a teammate loads one with `use_skill{name}` (`skills.go`), whose result is the body plus the library items named in the skill's `craft.txt` (up to 60k chars, `resultUpTo`). The library (`skills/library/{craft,style,template}`, `library.go`) is read with `read_reference{name}` as `group/name`; a role sees the groups in `skills/<role>/LIBRARY` (Designer: all three, Reviewer: craft) and each group has an `INDEX.txt` (`name: summary`) that feeds the prompt list. A folder item returns its md, css and html files (not `assets/`). Roles: Planner has `prd` (always); Designer (read, write, exec, ask) has `designer-workflow` (always, written here: find DESIGN.md, choose a style family, `design-brief`, template, `frontend-design`, self-check with craft, report), `design-brief`, `frontend-design`, `baseline-ui`; Reviewer has `design-review` (written here, five dimensions, Keep/Fix/Quick wins). Copied files (the three upstream skills, `library/craft` from Open Design, adapted there from Refero's MIT skill, 15 generic style families without brand packages, 11 templates) are byte-identical with licences beside them and listed in `skills/NOTICE.md`; never edit them, copy the new upstream file over. Brand design systems (stripe, apple...) are left out on purpose: they imitate real companies' trade dress. The size guardrail exempts the skills folder. Only the role with `WritesPRD` (the Planner) has its report document saved as `tasks.prd`; `deliver` returns any other role's document to the orchestrator as text. A first real run showed the Reviewer writing its scores as `document` despite its skill saying not to, and replacing the PRD: prompts are not a guard, the server enforces it. The Designer's design lives in DESIGN.md. `leadRules`: Designer after the approved PRD and before the Developer for screens; after both, a Reviewer with a "design review" brief, Fix list back to the Designer, two rounds. The lead makes sure the app runs before the review, because the Reviewer cannot start it. The `screenshot` tool (below) lets both of them look.
- **Plan stays in step.** A first real run left the Plan tab saying "In progress / Not started" for finished work: the lead called `update_plan` once and never again, however the prompt asks for it. The server now moves the plan itself (`planprogress.go`): the step whose title or detail names a teammate becomes active when `delegate` starts that role and done or failed when it reports (`trackPlan`; steps that name no role are left to the lead), and the lead's first `finish` on a team task is refused while steps are still pending or active, naming them, once per run (`planStale`, `runState.planWarned`). Solo tasks are untouched.
- **Shared plan.** The lead's `update_plan` is the team's plan; each new teammate is shown it (`briefWithPlan`, read fresh from the task) with its brief. Briefs carry objective, what to hand back, files or tools, and limits. Failed checks go back to the Developer through the lead, two rounds at most.
- **Guard rails.** A team is not capped by how many jobs it hands out (a first cap of 8 stopped a real ERP build); `Limits.MaxIdleJobs` (6) refuses the next job only after that many in a row that changed no file, ran no check and wrote no document (`idleJobs`). A refused job is an error result, not a failure. The solo workflow in `prompt.go` also skips the plan for a small change; the first step that changes or runs something moves a plan-less task from planning to working (`tool()`).
- **Who did what.** On a team task every event carries `Event.Agent`: teammates by `labelledEvents`, the lead by a run-scoped copy of the Runner (`leading`; a Runner is shared by every task, never mutate it). Handoffs also carry `Event.Model`; `Check.By` names who ran a verified check. The web Team tab (`logic/team.ts`) derives jobs from the thread, so nothing extra is stored.
- **Thread.** `Event.Agent` names the teammate; `EventHandoff` (`action` assigned, reported or failed) marks work changing hands.

## Models, effort and context

**Providers.** Anthropic Messages and OpenAI Chat Completions over plain HTTP. Gemini uses Google's OpenAI-compatible endpoint (`/v1beta/openai`) with the same client. A gateway works if it runs on the same computer. Every outgoing model call goes through `platform/egress`, which checks the real IP when the connection opens: hosted providers may reach only public addresses, gateways only loopback and never this server's own port, with no redirects and no proxy variables. API keys are sealed with AES-256-GCM (`platform/secretbox`) using `DATA_DIR/secret.key`.

**GitHub.** `modules/github`: each person connects their own account through a GitHub App (web flow with PKCE; tokens sealed, renewed on demand). Commands in a project get the owner's token and, on a socket of their own, `github.com`, `api.github.com` and `codeload.github.com`; sites never do.

**Effort.**
- A task keeps the effort it was started with (`tasks.effort`; empty uses the provider's default; a person's default is `preferences.default_effort`).
- Which levels are offered comes from the provider. A gateway that describes its models (9router does) decides per model; a model it says thinks like Claude gets Low to Max, with no None or Minimal.
- A gateway's model list is read again when a page asks for models, at most every 30 seconds (`Service.SyncStale`). An unreachable gateway keeps its list. Refresh does it at once.
- The OpenAI-style client sends `reasoning_effort` (this also reaches gateways such as 9router); the Anthropic client sends `output_config.effort`. An empty level leaves the field out.
- Every model call, including the summary that shortens a long task, uses the task's effort.

**Limits and context.**
- 40 model turns and 15 minutes per run (team tasks: see The agent team). No total token budget per task. A project runs one task at a time. Interrupted tasks are marked and can be continued.
- A model's context window is the size the person chose in Settings, else the size its provider reported when the key was verified (`model_catalog`; 9router, OpenRouter and Anthropic list it in `/v1/models`), else 1M for a name ending in `[1m]`, else 200K.
- **Too-long requests (own loop).** If a model refuses a request for length (`isOverflow`: a non-retryable `ModelError` whose message names the context or token limit), `askShorter` summarises once from a copy whose tool results are cut to 2,000 characters (the full request would not fit either), then asks again. Any other error still fails the task. This covers a window that was guessed too big (no provider report, so 200K).
- **Meter on a plan.** The program keeps and shortens its own conversation (this app never compacts it). `CLIResult.Used` is the tokens of its last model call: Claude's last `assistant` line (`input + cache read + cache creation + output`), Codex's `turn.completed` `input_tokens` (the whole turn's input, so it can overstate a turn with many calls; capped at the window). `Window` is Claude's `result.modelUsage[*].contextWindow`; else `provider.Service.ContextWindow` answers for `plan:*` ids from the plan's catalog (Codex `context_window` in `codex debug models`; Claude has none, so 200K). `planmeter.go` saves it for the lead only. A window the person sets for a plan's model lives in `plan_windows` (migration 038; `cliagent/adapter/sqlite/windows.go`, via `Plans.SetWindow`) and reaches the program only when set: Claude gets `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, Codex `-c model_context_window=`. An unset model passes nothing, so the program keeps its own size.
- Before a turn, when the conversation nears the window (window minus 33K), the model writes a summary of the task so far. The summary replaces the earlier messages in what is sent; the full history stays on record, and the thread shows "I shortened my notes to keep going".
- The task row keeps the last measured size and the window (`context_used`, `context_window`), shown as a meter. If no summary comes back the task goes on, and after three misses in a run it stops trying.

## Data, live updates, limits

### Project environment and external databases

Migrations 043 and 044 add `project_env_vars` and one `project_db_connections`
row per project. The Env store (`modules/env/adapter/sqlite`) seals every value
with `platform/secretbox`; list and save responses omit secret values. Names are
uppercase identifiers (64 characters max), except `PATH`, `HOME`, proxy names,
`LD_*`, `GO*` and `DOCKER_*`; projects have 50 variables maximum and values are
limited to 4096 bytes. The DB store also seals passwords and returns metadata
only. Its application service coordinates saving/removing the generated URL as
an Env secret.

HTTP routes are `GET/PUT /api/projects/:id/env`,
`DELETE /api/projects/:id/env/:name`, `GET/PUT/DELETE /api/projects/:id/db`,
and `POST /api/projects/:id/db/test`. All are owner-scoped. The DB test has a
10-second deadline and `databaseTestLimit` allows five calls per user each
minute. Probe errors are category-only plain messages; never return driver
errors or connection strings.

`runner.WithProjectEnv` loads values for sandbox commands and checks;
`site.Runtime.WithProjectEnv` covers project sites, and `bootstrap/taskcli.go`
adds them to CLI program runs. `MergeProjectEnvironment` preserves the fixed
base environment, including proxy values. Do not put values in prompts, logs,
task events or command text. Migrations are append-only and checksummed.

`platform/egress.PrivateAllowed` is for the server-side database probe only. It
allows public, private and loopback addresses, but rejects link-local,
unspecified, multicast, special-use ranges and the app's own port at dial time.
PostgreSQL uses pgx's dial function, MySQL uses a per-connector dial function,
and Mongo uses its custom context dialer after resolving and checking every
candidate IP. The sandbox remains network-disabled.

- **Your data** (`modules/mydata`): `GET /api/account/export` streams a zip built from sections that bootstrap assembles from the other features (`bootstrap/export.go`). `DELETE /api/tasks` clears a person's tasks, cancelling running ones. `POST /api/auth/delete` checks the password, then runs the erasers other features registered (tasks, then projects and their folders) before deleting the user row; the rest goes through foreign-key cascades.
- **Live updates:** task pages and the workspace follow changes over server-sent events (`GET /api/tasks/:id/stream` for steps and streamed text, `GET /api/stream` for list changes). A reconnecting client resumes from `Last-Event-ID`; the workspace falls back to a slow poll.
- **Rate limits:** sign-in, sign-up and the open OAuth endpoints are limited per visitor address; failed sign-ins also per account and address, so someone else's wrong guesses never lock you out. Expired sessions, codes, tokens and unused clients are swept every hour.
- **Migrations:** the schema changes only through numbered files in `internal/platform/database/migrations/`. Applied files are checksummed and can never be edited.

### Shared PostgreSQL provisioning

`POSTGRES_ADMIN_URL` is optional process configuration, never a project value.
It must include a database name in its URL path. The provision adapter uses a
10-second `PrivateAllowed` dial and a single admin
transaction pinned to the admin URL's database. It derives `p_<hash24>` from
the first 24 hex characters of SHA-256(projectID) for both role and schema,
quoting every identifier with `pgx.Identifier`. In order, the transaction
quotes the generated 32-byte password server-side; creates or reconciles a
`LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT` role with connection
limit 10; creates the schema or verifies its owner; revokes `PUBLIC` on
`public` and verifies that PUBLIC has neither `CREATE` nor `USAGE`; revokes the
role's direct database privileges then grants it `CONNECT`; and sets its
`search_path` to the project schema. PostgreSQL keeps database `TEMPORARY` for
`PUBLIC`, so do not describe effective database rights as CONNECT-only. The
`PUBLIC` schema revoke is database-wide, so the configured database must be
dedicated to this feature. Require `sslmode=require` or stronger and disable
DDL statement logging and `pg_stat_statements` on that database because role
passwords appear in role DDL.

Provision failures expose only safe categories, including
`manual_connection_exists` and `compensation_failed`. ProvisionShared refuses
to replace a saved manual connection. ProvisionShared, Save and Delete share a
per-project lock. The service snapshots the previous managed password and
`DATABASE_URL`; after rotation, a failed local save or Env write restores the
previous sealed connection, Env value and remote password using an independent
10-second context. Removing a connection does not drop remote objects.
Migration 045 adds the persisted `managed` flag. The optional integration test
uses `PG_ADMIN_TEST_URL` and skips when it is unset; point it only at a
disposable, dedicated database.

Revoking `PUBLIC` on `public` affects the whole database, so operators must use
a dedicated database. Some managed PostgreSQL services restrict role creation.

## Workspace screens (detail)

- **Sidebar:** New task, Search (Ctrl/Cmd+K), Inbox, All projects, recent tasks grouped by day with a status dot and relative time, and a collapsible Projects list. Settings and the account menu sit at the bottom. It is an icon rail on desktop and a drawer on phones.
- **Home:** one composer (a project picker that reads "Select a project" until chosen, a model and effort picker, and send), then a short "Needs you" list and what is running. There is no separate chat or approval-level choice: every message starts a task thread. The greeting is the one serif moment.
- **Inbox:** a list beside a detail pane, gathering what needs the user (a permission request, a question, a finished task to review, a task that could not finish). It is not a global task list.
- **Task:** a conversation next to a work panel. The user's message is a soft bubble; the assistant's reply is plain text. Consecutive actions fold into one expandable line; only questions, permission requests and results are cards. The work panel has Plan, Proof, Changes and Files, which become tabs on phones. Looking at files runs on its own; a step that changes a file or runs a check asks first. A question that needs no changes is answered in the thread and ends as Done, with no review step.
- **Settings:** a grouped left nav (AI, Preferences, Account) beside plain rows: label and short description on the left, control on the right, hairline dividers, no cards around single controls. Adding a provider opens a dialog using the shared `FormField` (visible label, hint in secondary text, error under the field once touched or submitted). Pages with editable values end with a sticky Save bar. On phones the nav becomes a scrolling row of tabs.
- **Status and approvals:** task status is always an icon plus a text label, never color alone. Permission requests show the exact action, a risk label and two choices (Allow, Don't allow). Project tiles pick `primary`, `secondary` or `accent` from the project id. The "Proven to work" stamp appears only for verified, passing checks. Screens never show sample data or pretend buttons. Destructive account actions ask for confirmation; deleting the account also asks for the password.
- **One project, one app.** A project is one folder and runs one app; the limit is per project, not per person: `Limits.PerUser` defaults to 0 (no cap) and `Total` to 20 (a guard for the machine), and zero always means no cap. `Service.Start` checks room before it stops the project's own app, because a refused start used to leave the project with no app. `leadRules` and the solo prompt tell the agent to list the project first and, when an app is already there and the person wants a different one, ask once "Replace the app that is here" or "Keep it and start a new project" (the agent cannot create projects, so for the second it tells the person to press New project). - **Files for the person.** `coding/adapter/http` serves the browser's own view of a project (session auth, owner only, confined like the agent's tools, secrets hidden by `domain.Denied`): `GET /api/projects/:id/files?path=`, `GET .../file?path=` (content, `hash`, `truncated`, `binary`), `PUT .../file {path, content, baseHash}`, `DELETE .../file?path=` and the SSE `GET .../files/stream`. A save goes through `Editor.WriteIfUnchanged`: `baseHash` is `domain.ContentHash` of the text the person opened (empty = the file must not exist), a mismatch is `ErrStale` (409 `changed`), so the agent's work is never overwritten quietly; the old content is backed up like any change. Statuses: added, modified, deleted, renamed; binary files carry no text; text over `MaxReadBytes` is cut and flagged. The page works out the lines (the server sends `before` and `after`): `@codemirror/merge` draws split (`MergeView`) and unified (`unifiedMergeView`) and `Chunk.build` counts the +/- of each file, so list and diff agree. Backups are pruned after 30 days, so the oldest tasks lose their `before`. ## Subscription sign-in through the real CLIs (plan and spike, 2026-10-19)

- **Why not a 9router-style token proxy.** (This is about routing a vendor's plan credentials. OpenAI's Sign in with ChatGPT for third parties is limited to selected partners. Re-read both pages before changing this.
