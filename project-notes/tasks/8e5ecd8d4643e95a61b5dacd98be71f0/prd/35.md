## Overview
Most tests call package internals with fakes, which makes them slow to maintain and easy to break without catching real bugs. The goal is to keep tests that exercise the real system through HTTP, MCP, the real DB, a browser or Docker. White-box tests stay only for super-critical logic, each with a written reason black-box testing cannot do the job.

## Goals and non-goals
- **Goals:**
  - Delete about 70% of the Go test files (estimate below).
  - Make black-box the default and enforce that with a registry and a guardrail.
  - Keep Fast quick and move slow checks to Full.
  - Record before and after CI times.
- **Non-goals:** Coverage targets. Rewrites of kept tests. New frameworks. A second server or port.

## Classification rules (decision procedure)
Apply in order to every test file and every named test:
1. **Does it drive only a public boundary?** That means HTTP, MCP, the built binary, a browser, Docker, or the real DB through the app. If yes, it is black-box and stays, unless rule 5 applies.
2. **Is the behavior in one of the six categories?** The categories are auth/authz; crypto/credentials; cross-user and cross-project isolation; sandbox/egress/SSRF/privilege; DB integrity, migrations and transactions; critical concurrency or data loss. If not, delete it.
3. **Can the harness trigger the failure deterministically?** If yes, delete the test and cover the behavior with a black-box scenario (add one if none exists). If not, retain it as white-box with a registry row.
4. **Delete coverage-chasing and mock-only tests.** This covers getters, constructors, trivial mappers, and tests that mostly assert on fakes.
5. **Delete duplicates.** A white-box test is a duplicate when a bootstrap or harness scenario already checks the same outcome.
6. **No security or data-integrity check disappears without a named replacement.** Anything deleted under rule 2 or 3 needs an equal or stronger test written next to it in the list.

## Harness design (small, no broad rewrite)
- **Location:** a new `internal/blackbox/` folder, with `harness/` plus scenario tests beside it. `AGENTS.md` Folder structure and the guardrails are updated in the same change.
- **How it starts the app:** it runs the built binary (`APP_BIN`) as a child process with `PORT` and `DATA_DIR` set to a temp dir and a free port. `scripts/smoke-test.sh` already uses these variables. It waits for `/api/health`, and `t.Cleanup` stops the process and removes the directory.
- **Helpers:** a restart that keeps the same data directory, a registered-user session helper, an HTTP client, and an MCP client (token plus headers).
- **Scenarios (at most six files):**
  1. Register, login and session.
  2. Cross-user isolation of projects, tasks, sites and files.
  3. MCP token scope and tool authorization.
  4. Secrets never appear in API responses (env, dbconn, github).
  5. Restart keeps data and the encryption key. This is the black-box counterpart to the `secretbox` key-persistence check.
  6. A second instance is refused and shutdown is clean.
- **Playwright:** one shared `scripts/e2e-run.sh <name>` replaces the duplicated start, wait and cleanup in the three shell scripts. Playwright is pinned and installed in CI. `make e2e` runs all three.
- **Docker-boundary tests:** these keep self-skipping unless `SANDBOX_TEST_IMAGE` and Docker are present. They run in Full only.

## Makefile and CI design
- **`make verify`** (the local gate and Fast): guardrails, frontend check, lint and build (no Vitest), `go mod tidy -diff`, `go test ./cmd/... ./internal/...` (the retained white-box tests plus bootstrap), Go lint, and the new `make blackbox`.
- **Fast** (`fast.yml`): the jobs stay parallel. `blackbox` runs after `build`, next to the existing smoke test. No Playwright, no Docker-boundary tests, no `-race`. Existing caching stays.
- **`make e2e`:** the three Playwright flows. **`make verify-full`:** `verify`, `e2e`, Docker-boundary tests, and `-race` on the retained concurrency packages.
- **Full** (`full.yml`): the `verify` job runs `make verify-full`, with a Playwright browser install and a Docker-based sandbox image test, before the merge to `main`. The jobs run in parallel and none are added to `fast.yml`.
- **Timing:** DevOps records the last three green Fast runs per job with `gh run view` before any change, and the same on the final commit. A Fast run that is slower than the baseline is a failure to explain, not to ignore.

## Risks
- **Docker:** the team's sandbox has no Docker, so Docker-boundary and Playwright tests are verified only in CI. Redeploy needs a host with Docker. If none is available, the final report will say it was skipped.
- **Full can't be tested before release:** Full can only be started from `dev` and it merges to `main`. The new E2E and Docker jobs are first proven on the next real release. A failure there blocks the merge, so it cannot break `main`.
- **Git write access:** the Researcher's `git fetch` failed because `.git/FETCH_HEAD` was read-only. DevOps must confirm it can fetch and push before slice 5.
- **Leftover code:** deleting tests may leave helpers or non-test code that lint flags as unused. Each slice includes cleaning that up.
- **Lost coverage:** deleted tests in the six categories could remove coverage. Rule 6 and the slice 2 list guard against it.
- **Larger Fast:** the new `blackbox` step adds time to Fast. That is the cost of having a real black-box smoke test, and it is measured in slice 10.
