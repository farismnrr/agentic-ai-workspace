## Database support today

- **Kinds and URLs:** `domain/connection.go` defines `Postgres`, `MySQL`, and `MongoDB` and builds connection URLs for all three (lines 11–22, 99–140). MongoDB defaults to `MONGODB_URL`; PostgreSQL and MySQL use `DATABASE_URL` (99–104).
- **Probes:** MySQL uses `go-sql-driver/mysql`; its current TLS setting is the driver’s built-in `"true"` configuration ( `adapter/probe/mysql.go:16–39`). MongoDB builds from the URL and pings with the Mongo driver (`adapter/probe/mongodb.go:21–43`). PostgreSQL has its own probe (`adapter/probe/postgres.go`).
- **Provisioning:** Only `adapter/provision/` implements project provisioning. It uses pgx to create a PostgreSQL schema and role (`provision/provision.go:66–89, 129–149`; `provision/apply.go`). No MySQL or MongoDB provisioner exists.
- **Settings are PostgreSQL-shaped:** `domain/shared_settings.go:20–25` stores one host/database/user/password and `SSLMode`; `SharedSettingsStore` has `Get` and `Save`, with no kind parameter (`application/shared_settings.go:21–25`). SQLite reads and upserts only singleton row `id = 1` (`adapter/sqlite/shared_settings.go:19–48`). Migrations 046 and 049 create that singleton and add its TLS-material columns (`migrations/046_shared_database_settings.sql:1–10`; `049_shared_database_tls.sql:1–3`). The HTTP routes and payload are `/api/settings/database`, without a kind (`adapter/http/shared_settings.go:22–46`). `DatabaseTab.svelte` labels the settings “Shared PostgreSQL” (`web/src/features/workspace/settings/DatabaseTab.svelte:144`); its API types are PostgreSQL’s six `SSLMode`s (`database-api.ts:3–13`).
- **Reusable vs PostgreSQL-specific:** The domain connection kind, URL construction, probe abstraction, cipher interface, secret handling, and shared UI field components can support more kinds. `SharedSettings`, SSL mode handling, singleton persistence, pgx TLS construction, the PostgreSQL `Provisioner` interface, and `sharedAdminURL` are PostgreSQL-specific (`bootstrap/dbconn.go:83–115`). `go.mod` already pins `go-sql-driver/mysql v1.10.1` and `mongo-driver/v2 v2.9.2` (`go.mod:5–18`); no new driver dependency is indicated.

**Smallest settings direction:** persist one settings record per kind, either adding `kind` to a keyed table or using a kind-keyed table, and pass the kind through the store/service. Add `/api/settings/database/:kind` GET/PUT routes or an equivalent kind field in the current API. Keep PostgreSQL SSL modes specific to PostgreSQL; map the shared three TLS choices to each driver’s TLS config rather than treating them as PostgreSQL `sslmode` values.

## Isolation and TLS references

- **MySQL:** MySQL documents `CREATE DATABASE`, `CREATE USER`, and database-scoped privileges such as `GRANT ... ON db.*`; its account docs warn that cleartext passwords can appear in server/client logs. Generate a project-specific database and password, scope the user’s grants only to that database, and use validated/generated identifiers with correct quoting. [CREATE DATABASE](https://dev.mysql.com/doc/refman/8.4/en/create-database.html), [CREATE USER](https://dev.mysql.com/doc/refman/8.4/en/create-user.html), [GRANT](https://dev.mysql.com/doc/refman/8.4/en/grant.html).
- The MySQL Go driver supports `mysql.RegisterTLSConfig` and referring to the registered name with `tls=custom`; its docs warn against skip-verification and plaintext fallback. The driver also provides `Config.FormatDSN` for DSN construction. A project app can build an in-memory TLS config from `DATABASE_SSL_CA` and use it through the driver; no file is required by this driver path. [Driver README](https://github.com/go-sql-driver/mysql), [DSN/config docs](https://github.com/go-sql-driver/mysql/blob/master/dsn.go).
- **MongoDB:** create a database per project, create a user scoped to that database with the `readWrite` role on it, and set the project connection URI’s `authSource` to the database where that user is defined. MongoDB documents `createUser`, role scoping, and URI auth-source behavior. [Database users](https://www.mongodb.com/docs/manual/core/security-users/), [`createUser`](https://www.mongodb.com/docs/manual/reference/method/db.createUser/), [connection string formats](https://www.mongodb.com/docs/manual/reference/connection-string-formats/).
- The Mongo Go driver supports custom CA and client certificates through `SetTLSConfig(&tls.Config{RootCAs, Certificates})`; a project app can build this in memory from `DATABASE_SSL_CA`. Do not set `InsecureSkipVerify` for normal verification: MongoDB warns that it disables certificate and hostname validation. [Go driver TLS guide](https://www.mongodb.com/docs/drivers/go/current/security/tls/).
- A per-project MongoDB “database” is a logical namespace, not the same physical isolation boundary as a server or cluster. MongoDB authorization should be tested to confirm each generated user can access only its assigned database; avoid broader roles. This is an implementation risk inferred from the role-based model, not a project behavior already implemented.

## Logged-in screenshot path

- The built-in `screenshot` tool is for a running **project site**: it accepts path/device/y/overview and captures through a separate one-shot sandbox container (`agents/implementation-notes.md:79`; implementation: `internal/bootstrap/agenttools_shot.go`, `internal/modules/site/adapter/runtime/capture.go`, `sandbox/capture/capture.ts`). It has no documented login, cookie, or Workspace-origin options. The standard site preview intentionally strips Workspace cookies and cannot test app login (`docs/preview-auth.md:3–5, 13–18`).
- There is no seed/demo account mechanism evident in the inspected docs or bootstrap paths. Registration is available at `POST /api/auth/register`; it creates a browser session and sets an HttpOnly `session` cookie (`internal/modules/account/adapter/http/handler.go:58–71, 111–120`). `DATA_DIR` is configurable (`internal/platform/config/config.go:95–112`) and `ADMIN_EMAIL` selects the admin address (same file, lines 18–20 and 112).
- **Recommended recipe:** DevOps starts an isolated local app with a temporary `DATA_DIR` and a separate port, using the normal build/run workflow. Register a throwaway account with `curl` against that local app, using the configured `ADMIN_EMAIL` if the Database settings page must be admin-visible. Capture the `Set-Cookie` response in a local cookie jar, then use Playwright against the same local origin with that cookie jar or a browser context cookie to open `/app/projects` and the project detail URL at desktop and mobile viewports. The browser should be Playwright, not the site screenshot tool; `scripts/e2e-thread.ts` demonstrates authenticated browser navigation, but it does not document an app screenshot recipe. A separate seeded project may be needed because the app has no demo data path evidenced here.
- This is a recommended recipe assembled from the registration and configuration code; I did not start the app or run it.
