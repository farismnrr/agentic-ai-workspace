# Fix Task Bubble Lifecycle, Live Streaming, and External Task Chat Routing

Repository: `farismnrr/agentic-ai-workspace`  
Target branch: `dev`  
Baseline investigation: `751c985` (verify current HEAD before proceeding)

## Objective

Fix inconsistent task chat bubbles and enable users to communicate with the internal orchestrator from external tasks created by ChatGPT, Gemini, or other MCP clients.

Both internal and external work must have reliable, persistent, real-time task timelines.

**Important:** External assistants and the internal orchestrator are independent execution systems. Never enqueue an internal agent merely because an external task was created or updated.

## 1. Confirmed findings to investigate

Previous source inspection identified these issues.

### A. External task composer conflicts with backend

`web/src/features/workspace/task/TaskScreen.svelte`

- The composer is enabled when status is `review`, `done`, or `failed`.
- The condition does not distinguish external and internal tasks.

`web/src/features/workspace/logic/task-actions.ts`

- `follow()` always calls `sendMessage()`.

`internal/modules/task/application/service.go`

- `FollowUp()` explicitly rejects tasks with `Source != ""` using `ErrWrongState`.

Result:

- UI accepts a user message.
- Backend returns HTTP 409, `wrong_state`.
- UI shows `That is not possible right now.`

Do not fix this by simply deleting the backend's external-task guard.

### B. SSE cannot reliably reconcile updated events

`web/src/features/workspace/logic/thread.ts`

- Incoming events are filtered using `event.seq > last`.
- Existing events are not reliably reconciled when their contents change.

`internal/modules/task/adapter/sqlite/work_calls.go`

- `UpdateWorkCall()` updates an existing event while preserving its sequence.

`internal/modules/task/adapter/http/stream.go`

- The stream sends newly appended events after the cursor.

Result:

An existing event may transition from `running` to `finished`, but the browser does not update the corresponding entry until a complete refresh.

Investigate the full implications for reconnects, dropped notifications, and simultaneous updates.

### C. External assistant messages can lose bubble semantics

Investigate:

- `internal/modules/coding/adapter/mcp/tools_log.go`
- `internal/modules/coding/adapter/mcp/guard_thread.go`
- `internal/modules/coding/adapter/mcp/guard_work.go`
- `internal/modules/task/application/work_calls.go`
- `web/src/features/workspace/task/thread/blocks.ts`

Explicit work-session messages may be recorded as action events instead of preserving their original user/assistant role.

Ensure conversation messages retain conversation semantics rather than being collapsed into action groups.

### D. External streaming and persistence are incomplete

Internal models already support text deltas.

External MCP clients currently report progress through tool calls, so their actual token stream may not be exposed to this server.

Also investigate the current `log_message` success reporting and whether errors during thread persistence are silently ignored.

A successful persistence response must accurately represent the persistence guarantee it claims.

## 2. Required behavior: task bubbles

### Internal orchestrator

- Show the user's message immediately after the request is accepted.
- Show an AI activity indicator as soon as execution starts.
- Render incoming model text incrementally.
- Replace the transient streaming draft with its persisted event without duplicate bubbles.
- Keep bubbles ordered by authoritative event sequence.
- Preserve existing messages during reloads, reconnects, and route changes.
- Never discard unsaved streamed text without a clearly defined reconciliation or failure strategy.

### External ChatGPT/Gemini

- Create and publish the task promptly when `begin_work` succeeds.
- Display the task in the task list and timeline while work is still active.
- Show a working indicator before the first research, plan, action, or result event.
- Preserve `user` and `assistant` messages as actual chat bubbles.
- Keep tools, research, planning, roles, and execution results as appropriately typed events.
- Update running actions when they finish.
- Preserve the same task identity across progress updates.
- Ensure task completion updates the existing timeline rather than creating duplicate messages.

Support both explicit external work sessions (`work_id`) and the supported legacy connected-app recording flow.

### Streaming limitation

Do not pretend that arbitrary ChatGPT/Gemini tokens are available.

When the client does not expose token-level output, show an accurate active-work indicator and update the timeline whenever actual messages or progress events arrive.

If token-level output is supported through an existing, authorized integration, use it without introducing unsafe credential handling or an unrelated transport.

## 3. Required behavior: user chat on external tasks

The user must be able to send messages from an external task's chat interface.

**Routing contract:**

- Internal task chat → internal orchestrator.
- External assistant activity → external assistant's own workflow.
- User sends a message from an external task → internal orchestrator.
- The external assistant must not automatically receive that message or be impersonated by the orchestrator.

### Recommended architecture

Implement a task-linked internal orchestrator conversation, while keeping external task execution independent.

Requirements:

1. Preserve the existing external task ID, source, work ID, and ownership.
2. Create or reuse an explicitly linked internal orchestrator task for user-initiated chat.
3. Persist the relationship server-side, using a minimal, well-defined schema or application contract.
4. Provide the orchestrator with relevant context from the external task: the user's request, available plan, research, progress, and verified outcomes.
5. Keep external assistant claims distinguishable from server-verified evidence.
6. Do not allow the orchestrator to modify external work lifecycle state.
7. Keep both execution histories inspectable, with clear actor/source attribution.
8. Make the linked conversation accessible from the originating external task, preferably without losing the user's current context.
9. Ensure follow-up messages reuse the correct internal conversation.
10. Avoid multiple internal tasks being created by retries, double-clicks, or concurrent requests.

Inspect existing application boundaries before choosing the exact implementation. Do not build a second orchestrator implementation or force internal messages into the external assistant's transcript.

If the existing architecture suggests a simpler design that preserves every invariant above, use it and document the reason.

### UX expectations

- A valid message must not return `wrong_state` merely because the originating task is external.
- The composer must reflect the actual capabilities of the selected execution path.
- Sending a message should clearly indicate that the internal orchestrator is responding.
- External assistant progress must remain visible and independent.
- Preserve typed text and attachments on failed requests.
- Existing internal conversations must continue behaving as before.
- If no internal AI model is configured, show the actual configuration problem and recovery action.

Do not silently route messages to ChatGPT/Gemini, and do not silently execute internal agents on ordinary external progress updates.

## 4. Reliable real-time event synchronization

Review the existing SSE implementation comprehensively.

Implement a reliable strategy supporting both:

- Appending new events.
- Updating previously persisted events.

Requirements:

- Stable event IDs and deterministic ordering.
- Upsert/reconciliation semantics for changed events.
- No duplicate messages on reconnection.
- No stale `running` action after completion.
- Recovery after missed SSE notifications.
- Consistency between `/api/tasks/:id/events` and `/api/tasks/:id/stream`.
- Safe handling of late or out-of-order network responses.
- Reliable task-list refresh when an external task begins.
- Proper subscription cleanup.
- No unnecessary polling that increases load.
- No unbounded client memory growth or duplicate event accumulation.

A sequence cursor alone is insufficient for updated historical events.

Use the smallest coherent change consistent with the current architecture. Do not unnecessarily replace the existing SSE infrastructure.

## 5. Persistence and integrity

Review transactional behavior and error handling.

Guarantee:

- Accepted chat messages have durable persistence semantics.
- Existing event updates cannot silently fail while the UI reports completion.
- Failed persistence is not misrepresented as success.
- Event ownership, actor identity, source, and work-session identifiers remain trustworthy.
- Duplicate requests are handled safely.
- User/project authorization is enforced server-side.
- Cross-project task references are rejected.
- CSRF protection remains enforced for cookie-authenticated mutations.
- External MCP tools cannot acquire internal orchestrator privileges through the new linkage.

Preserve the existing external work security and tool permission boundaries.

### End-to-end scenarios

1. Internal task creation → streaming → persisted response → completion.
2. ChatGPT/Gemini work session → active task visible → role/progress events → complete.
3. Long-running external command → running event → finished event, without page reload.
4. External task → user sends chat → internal orchestrator responds.
5. External work and internal linked conversation active concurrently.
6. Stream disconnection → reconnect → correct event history.
7. Browser refresh during active streaming.
8. User changes tasks while updates continue.
9. Server-side error or persistence failure.
10. Legacy external task behavior.

Use the existing test infrastructure and Playwright where practical.
