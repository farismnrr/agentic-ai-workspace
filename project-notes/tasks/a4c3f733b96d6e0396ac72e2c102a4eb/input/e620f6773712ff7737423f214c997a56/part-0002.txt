## 7. Engineering constraints

- Follow Clean Architecture, SOLID, and existing module boundaries.
- Keep task business logic in the task domain/application, not the UI.
- Avoid god services and unnecessary cross-module imports.
- Use strict TypeScript and existing Svelte patterns.
- Reuse existing daisyUI components, semantic theme values, and chat components.
- Respect repository file/function size limits.
- Do not weaken test, lint, security, or CI guardrails.
- Do not modify generated build artifacts manually.
- Do not change consumer authentication flows.
- Do not overwrite unrelated data.
- Avoid unrelated refactoring.

Update human-readable documentation in `docs/` and relevant agent-only knowledge in `agents/`.

## 8. Verification and delivery

Once implementation is complete:

1. Run relevant focused tests.
2. Run `make verify`.
3. Run browser and integration regression tests.
4. Inspect affected UI visually at desktop, tablet, and mobile sizes.
5. Confirm the original error is resolved for the intended user-chat flow.
6. Confirm external sessions never automatically enqueue an internal agent.
7. Review the final diff for unrelated changes, regressions, and security concerns.
8. Commit only task-related changes to `dev`.
9. Push normally to `origin/dev`, without force.
10. Wait for Fast CI on the exact commit.
11. If CI fails, diagnose, fix, and verify again.
12. Once CI is green, follow the repository's approved `make redeploy-dev` workflow when the target Docker runtime is available and safe to access.
13. Verify `/api/health` and affected live behaviors after deployment.

Do not claim a test, CI check, or deployment succeeded unless it was actually verified.

If infrastructure prevents live verification, report the blocker and distinguish local test results from deployment verification.
