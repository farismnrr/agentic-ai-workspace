# PRD — Consolidated 9-Role Agent Team with Enforced Execution Boundaries
**Branch:** dev. **Issue/task:** 62b3bf7e9fe7d2ea2f554e43fc70ac3f. **Status:** approved for implementation by the person. **Research:** research.md in the same task.

## Goal and scope
Reduce built-in roles from 13 to 9: Orchestrator, Researcher, Business Analyst, Planner, Architect, Developer (absorbs Designer+Media+Documents), QA (absorbs Reviewer), Security, DevOps. Both internal delegation and external MCP must use the same server-authorized, fail-closed effective permissions, not just role prompts. Preserve the single task per issue. Swift defaults: focused black-box tests, not full test/CI suites.

## Policy (functional)
- **Orchestrator**: coordinate, assign, report. Internal team lead cannot edit/test/deploy. Preserve existing solo Swift behavior as a *documented exception* until explicitly changed.
- **Researcher**: read/web/research notes only. **BA**: requirements; **Planner**: plans/PRD; **Architect**: read/review architecture. None may edit/exec/deploy.
- **Developer**: read, source/UI/images/media/docs authoring and modifying, controlled image search/download, MoLab, screenshot/visual inspection. No `run_task`, arbitrary `run_command`, `start_site`, `deploy_extension`, `approve_plan` or direct CI/release operations. Migrate design/media/document playbooks and library references. For UI change require visual inspection before reporting completion when runnable preview exists; let DevOps start app.
- **QA**: read, code review, named checks/tests, verdict; `ChecksLook` merged. No direct source edits, general shell, app launch/deploy/approval by default; optional plan approval only via separate human switch and OAuth coding:approve. Distinguish code review (same external assistant) from independent reviewer (separate internal delegate).
- **Security**: read, bounded security scans/commands; no write, arbitrary shell or deploy.
- **DevOps**: build, package, start/stop site and deploy, edit only operation/config surfaces when explicitly needed. No application source editing or test ownership. Generic shell against writable source is **not allowed** as a trust boundary. Where current runtime only supports unrestricted command execution, do not falsely claim strict enforcement: introduce constrained execution or blocked operation and document limitations.
- **Custom roles**: respect human-configured access but cannot bypass protected built-in role boundaries by renaming; do not give automatic forbidden high-impact mutation/exec privileges without explicit ownership and scope.

## Security & workflow
Effective access intersection = authenticated identity + scoped project/task + enabled role + exact operation + safe filesystem/path scope + global user tool toggle + OAuth scope + human approvals. Check at execution, including after role switches and disabled/revoked roles. Tool denial must be actionable. Prefer typed capabilities and read-only filesystem mounts for QA and DevOps instead of Bash keyword blocking. Existing sandbox and credential/egress protections must remain.
- External `set_role` may switch among planned roles in same task; restrict execution of unplanned high-risk roles (Developer/DevOps/QA) until explicitly assigned/approved, and never claim an external self-switch constitutes independent QA review.
- Approval default is human; preserve idempotent retry for approved/closed work.
- Existing historical events preserve original role names and task IDs; retired role aliases resolve to new role **without restoring old Exec/Write**. Migrate persisted saved teams, disabled flags and model preferences. Users must not see duplicate old roles or lose custom roles.

## Non-regressions
- MoLab Developer-only, ephemeral URL/token in chat, task reused; no stored credentials or egress process.
- A Developer can still make UI/media/doc artifacts through task-specific capabilities. If strict no-shell removes necessary artifact processing, introduce safe typed tools or leave an explicit follow-up; no silent removal.
- Internal team role-based UI screenshot requirement and QA independent reviewer gate still work, including verification after last Developer change.
- Existing legacy pending role plans/work tasks and review references remain readable; active sessions rebase role on next call without opening a second task.

## Black-box acceptance
1. Nine built-in roles in API/settings and no legacy duplicates after save/reset/restart; old saved roles map to merged roles and historical labels remain.
2. Developer can edit source and use MoLab, cannot run tests or deploy; cannot start apps. Visual and media/doc capabilities preserved and previewed when applicable.
3. QA review + allowed checks, no edit/deploy/general shell; cannot change source via nested scripts or named tests. Security likewise.
4. DevOps can build and ship approved release artifacts, but cannot edit source or execute QA tests via direct tools, scripts, shells, git hooks or custom role escalation.
5. External and internal role enforcement identical for each operation; broad OAuth/user tool switches don't expand role; disabled-role/closed-work denies; role switching keeps one task.
6. Separate human approval still required for plan approve and high-impact operations; no fake independent review.
7. Black-box connector, team execution, review/approval, MoLab and affected frontend checks pass. If hard isolation is not achievable with existing runner, report it as unresolved and do not describe as secure.
