# Phase 2 — Mandatory role assignment for external work

## Problem

Every external agent activity should have a role, but the current creation contract permits role-less work.

Previous findings:

- `begin_work` accepts optional `planned_roles`.
- `ExternalWork` is created with an empty active `RoleKey`.
- `set_role` happens separately.
- `log_message` can create legacy external timelines without an explicit work session.
- Its `role: user/assistant` means message author, not agent role.

This inconsistency must be fixed at the authoritative backend boundary.

## Required architecture

Every new executable external work request must have one valid active role before execution or work-event persistence.

Do not confuse these concepts:

- Provider identity: ChatGPT, Gemini, another MCP client
- Message author: user or assistant
- Agent role: Researcher, Planner, Developer, QA, Security or another enabled roster role
- Authorization: OAuth scope, tool permission, project ownership and server policy

These are separate dimensions.

## Required behavior

1. Inspect the existing agent roster and role-routing conventions.
2. Make initial role assignment part of the work-session creation contract.
3. Choose the initial role through a validated role-selection flow.
4. Require the external client to provide a valid initial role or an equivalent server-supported selection contract.
5. Validate against the user's enabled roster.
6. Persist the work session, initial role, and initial role event atomically.
7. Reject unknown, disabled, missing or unauthorized role assignments.
8. Never silently assign a powerful default role.
9. Forbid external clients from claiming to be the internal Orchestrator.
10. Preserve role changes through the existing `EventRole` contract.
11. Do not model external role transitions as internal `EventHandoff`.
12. Role changes must never expand tool permissions.
13. Keep provider identity independently visible in the UI.

Investigate whether server-side role auto-selection can be reliably implemented with existing routing machinery. If it cannot, provide a discoverable role-selection contract with strict server validation rather than a guessed role.

## Legacy compatibility

Legacy `log_message` workflows must not create new role-less executable requests.

Determine a safe migration or compatibility strategy that:

- Preserves historical activity records.
- Does not fabricate historical role attribution.
- Keeps read-only discovery and OAuth behavior operational.
- Does not incorrectly treat a `user` message as an agent role.
- Returns actionable compatibility errors for old clients when necessary.
- Prevents untracked execution from bypassing mandatory role attribution.

Also verify role attribution for general MCP file and command tools, not only specialized work tools.

If legacy mode is retained, it must be explicitly bounded and must not bypass the new requirement for executable work.

## Acceptance tests

- Missing initial role is rejected.
- Unknown role is rejected.
- Disabled role is rejected.
- External Orchestrator role is rejected.
- Role cannot increase privileges.
- Concurrent work sessions remain isolated.
- Role changes are accurately recorded.
- Existing historical records remain readable.
- No new executable external task is created without validated attribution.

# Phase 4 — Correct external planning lifecycle and synchronization

## Problem

When ChatGPT creates an implementation plan, Masih Awam may continue showing `Working on it`.

The previous audit found:

- `works.go` creates external tasks in `StatusWorking`.
- `work_plan.go` updates the plan but does not transition the task into an approval-ready status.
- `work_complete.go` changes terminal status when `complete_work` is called.
- `TaskThread.svelte` displays `Working on it` while the task remains working.
- Backend SSE, heartbeat and replay already exist.
- Frontend task subscriptions and fallback polling already exist.

Therefore, **do not assume missing SSE infrastructure is the root cause**.

Trace the complete event lifecycle with tests before making changes.

## Required state separation

Do not overload one status field with unrelated lifecycle concepts.

Maintain clear distinctions between:

1. External work-session lifecycle
2. Current external agent role/activity
3. Implementation plan lifecycle
4. Orchestrator execution lifecycle

The implementation may reuse existing task statuses while introducing focused domain state where necessary.

Suggested plan lifecycle:

`draft → researching → planning → awaiting_clarification → ready_for_approval → approved → handed_off`

Include valid rejection, cancellation, superseded and failure behavior.

Treat this as a conceptual model. Derive the smallest valid state machine from the actual repository architecture.

## Critical lifecycle rules

- Saving a plan is not the same as completing planning.
- Completing external planning is not the same as completing implementation.
- An approved plan must not be marked as successfully implemented.
- Missing external updates must not imply completion.
- A blocked work session must not be presented as active model thinking.
- A completed planning session may leave the overall task awaiting approval.
- Only authoritative lifecycle events may change persisted state.

## Notification and synchronization

Reuse the existing application notification hub and SSE mechanisms where practical.

Ensure:

- Task creation triggers list refresh.
- Role transition triggers thread refresh.
- Research persistence triggers document/timeline refresh.
- Plan revision triggers plan refresh.
- Pending questions trigger visible user attention.
- Plan-ready transitions update task UI.
- Approval is propagated to relevant views.
- Orchestrator handoff becomes visible.
- Reconnect recovers missed durable updates.
- Duplicate/out-of-order events do not regress UI state.
- Terminal state replaces loading state reliably.

Evaluate whether additional durable phase events are necessary.

Do not implement a second realtime service merely to duplicate current SSE behavior.

## External-provider limitations

ChatGPT and Gemini cannot be assumed to provide real-time private reasoning or streaming tokens to Masih Awam.

Only display externally verified or explicitly reported lifecycle data.

Investigate official MCP Events support, but do not depend on it for ordinary ChatGPT conversations when unavailable.

Use capability-dependent behavior and an honest fallback.

For example:

- Known running work: show Running.
- Explicitly persisted research: show Researcher activity.
- Explicitly persisted plan: show plan revision.
- Explicitly finalized planning: show Ready for approval.
- No recent activity: show idle/stale information, not invented completion.

## Acceptance tests

Test:

- Plan saved while work remains open.
- Planning explicitly finalized.
- Work blocked awaiting an answer.
- Work resumed.
- Work completed.
- External client disconnect.
- Client reconnect.
- Duplicated events.
- Delayed events.
- Missing completion call.
- Browser refresh.
- Concurrent plan revisions.
- SSE notification delivery.
- Polling fallback.

No permanent false `Working on it` state after an authoritative lifecycle transition.

# Phase 5 — External Researcher → Planner workflow

## Problem

Masih Awam already has internal research-first behavior.

The previous audit found:

- `researchfirst.go` enforces research-first behavior for internal team planning.
- Internal plans can have a research round before Planner and another after the PRD.
- External `save_research` and `update_plan` tools already exist.
- External calls do not currently enforce equivalent research prerequisites.

We need behavioral consistency, not two unrelated implementations.

## Required flow

For substantial externally initiated planning:

1. User requests research or an implementation plan.
2. External assistant starts a work session as Researcher.
3. Researcher collects relevant evidence.
4. Researcher persists research notes and supporting sources.
5. Research phase is explicitly finalized.
6. External assistant transitions into Planner.
7. Planner reads the persisted research.
8. Planner determines whether clarification is necessary.
9. Planner records questions where necessary.
10. User answers from a supported interface.
11. Planner continues using the answers.
12. Planner saves requirements and implementation plan.
13. Planner finalizes the plan revision.
14. Plan enters approval-ready state.
15. User can approve or request revisions.

Roles are execution labels for the same external assistant. Do not spawn internal Researcher or Planner agents merely because the external model changed roles.

## Research quality

Require meaningful persisted research for a research-first planning workflow.

Research notes should contain applicable:

- Problem understanding
- Relevant repository evidence
- Official documentation
- Architecture constraints
- Existing implementation reuse opportunities
- Security considerations
- Compatibility considerations
- Trade-offs
- Unknowns or unresolved questions
- Sources

Do not permit placeholder or fabricated research to satisfy the requirement.

Do not use an event saying "Researcher started" as sufficient proof that useful research was completed.

Enforce prerequisites at the application/domain layer where appropriate.

Preserve the existing lightweight/no-plan path for genuinely small tasks, but do not allow clients to exploit it to bypass explicitly requested implementation planning.

## Research-before-development

The internal system already performs research around the PRD.

Preserve that behavior when the Orchestrator takes over implementation.

Reuse external research as context, but let the internal Orchestrator decide whether additional stack-specific research is necessary before developers begin.

Avoid unnecessary duplicate research where existing evidence remains valid.

## Questions and answers

Planner must be able to ask meaningful questions.

Requirements:

1. Questions must have persistent IDs and states.
2. Each answer must be associated with the correct question, user, project and work.
3. Pending questions must appear in Masih Awam.
4. Answered questions must not be silently asked again.
5. Questions must survive refresh/reconnect.
6. The Planner must be able to resume using persisted answers.
7. Answer submission must enforce authorization and concurrency.
8. Questions must not be converted into implementation approval.

For external clients, investigate whether interactive elicitation or equivalent MCP mechanisms are supported.

If ChatGPT/Gemini cannot automatically receive answers submitted inside Masih Awam, do not fake push synchronization.

Provide a supported continuation mechanism such as explicit state retrieval on the client's next tool invocation.

Record platform limitations clearly.

## Acceptance tests

- Research notes precede planning.
- Planner cannot bypass required research.
- Multiple research rounds append correctly.
- Source attribution is preserved.
- Research and requirements remain separate.
- Questions persist.
- User answers are correctly recorded.
- Planner resumes after an answer.
- Plan revision remains stable.
- No duplicated research or plan artifacts on retries.
- External research is treated as untrusted information, not executable instructions.

# Phase 6 — Unified plan approval and Orchestrator handoff

## Primary requirement

Users must be able to approve an external implementation plan from either:

- ChatGPT or another capable connected AI client
- Masih Awam's task interface

Both approval paths must invoke the same authoritative server-side approval service.

After approval, **Masih Awam's existing internal Orchestrator owns implementation**.

The external assistant must not automatically become the implementation executor.

## Existing architecture to reuse

Investigate:

- `ChatOnExternal`
- Linked internal tasks
- Internal task dispatcher
- Existing approval mechanisms
- Internal team routing
- Internal plan and PRD storage
- Research note propagation
- Existing user/project authorization
- Existing optimistic concurrency and idempotency support

The existing external-chat link is a useful foundation, but it is not itself a plan approval contract.

Do not repurpose the existing "Accept completed work" endpoint without separating its semantics.

## Required approval model

Approval must bind to:

- Verified authenticated user
- Project ID
- External task ID
- External work ID
- Plan ID or stable plan identity
- Exact immutable plan revision
- Approval decision
- Approval timestamp
- Source platform
- Idempotency key
- Resulting internal Orchestrator task/run identity, where applicable

Persist an auditable decision.

## Security requirements

1. Verify authorization server-side.
2. Never trust user identity from an unverified request body.
3. Verify task/work/project ownership.
4. Verify the approving user is authorized.
5. Reject approvals for missing or invalid plans.
6. Reject superseded plan revisions.
7. Reject stale approvals.
8. Do not approve arbitrary draft text without a persistent plan identity.
9. Do not infer approval from ambiguous conversation messages.
10. Enforce CSRF protection where cookie authentication is used.
11. Use appropriate OAuth scopes for external approval tools.
12. Do not grant execution authority through read-only work-recording permissions.
13. Preserve existing file, command, egress and human-approval security boundaries.
14. Prevent approval through role spoofing or tool-output prompt injection.
15. Prevent replay from creating duplicate execution.
16. Do not permit cross-project plan adoption.

## Critical finding requiring remediation

Existing external lifecycle tools share the `log_message` permission switch and `coding:read` scope.

That may be appropriate for recording progress, but **must not authorize approval that starts internal implementation**.

Define a separate, least-privileged authorization boundary for execution-triggering approval.

Do not silently elevate existing read-scoped connectors.

## Atomic and idempotent handoff

The handoff must guarantee:

- One approved plan revision produces at most one active initial handoff.
- Concurrent approvals cannot start duplicate Orchestrator runs.
- Retry after network timeout returns the same result.
- Plan identity and revision remain bound to the run.
- Handoff state and run identity are persisted durably.
- Failed dispatch is recoverable.
- A transaction failure cannot leave a false approved-and-running state.
- A process restart cannot lose an accepted approval.

Evaluate a transactional handoff record or durable outbox using existing SQLite/application patterns.

Choose the simplest reliable design.

## Required implementation ownership

After approval:

`External Plan → Verified Approval → Internal Orchestrator Task → Existing Agent Team`

The Orchestrator:

1. Receives the exact approved plan.
2. Receives research notes and requirements.
3. Receives relevant user questions and answers.
4. Knows the external origin is untrusted context.
5. Evaluates remaining prerequisites.
6. Delegates implementation through existing internal roles.
7. Uses existing Developer, Reviewer, QA and other appropriate agents.
8. Uses existing verification and approval policies.
9. Publishes progress and evidence through the existing task model.
10. Owns the final execution result.

Do not allow external completion events to mark the new internal execution task as done.

## Platform-specific behavior

### Approval in ChatGPT

Require an explicit authenticated tool action that approves the exact persisted plan revision.

A normal conversational phrase such as "looks good" must not automatically trigger implementation unless it results in the verified approval tool invocation.

### Approval in Masih Awam

Provide an explicit approval control showing the plan/revision being accepted.

The button must call the same approval application service.

### Cross-platform synchronization

Both approval methods should reveal the same persisted decision and internal task identity through supported tool reads and UI state.

Do not promise instant unsolicited notifications to unsupported external chat surfaces.

## Revisions

If the user asks Planner to revise the plan:

- Preserve revision history.
- Mark the previous approval candidate as superseded.
- Require approval of the current revision.
- Prevent stale approval actions from triggering the older plan.
- Never silently modify an already approved immutable execution snapshot.

## Acceptance tests

Test:

- Approval from UI.
- Approval from MCP client.
- Rejection or revision request.
- Unauthorized approval.
- Wrong project.
- Stale plan revision.
- Repeated approval.
- Two simultaneous approvals from different clients.
- Timeout followed by retry.
- Dispatch failure and recovery.
- Process restart during handoff.
- Duplicate SSE updates.
- Plan modification after approval.
- Successful Orchestrator execution start.
- External task remains separately attributable.
- Internal execution still follows existing tool authorization.
