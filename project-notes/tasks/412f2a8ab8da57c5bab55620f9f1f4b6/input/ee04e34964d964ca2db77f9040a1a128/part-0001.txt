# Phase 1 — Accessible task status indicators

## Problem

Some task indicators still rely on colored dots. People with color-vision deficiencies cannot reliably interpret their meaning.

The previous audit found:

- `StatusDot.svelte` already renders accessible icons.
- `StatusBadge.svelte` already uses icon plus label.
- `SidebarTaskRow.svelte` still renders a colored status dot.
- Some sidebar task states do not display a visible status indicator at all.

Avoid creating another redundant status component.

## Required behavior

Use consistent icon-based status semantics:

| Status | Visual indicator |
|---|---|
| Queued | Clock |
| Planning | Document or planning indicator |
| Working | Animated loader |
| Needs input | Question mark |
| Review | Review/attention indicator |
| Completed | Check |
| Failed | Cross/error |
| Cancelled/stopped | Cancellation indicator, if supported by the actual domain model |

The existing domain statuses are authoritative. Do not fabricate additional statuses purely for appearance.

Requirements:

1. Reuse the centralized `statusMeta` mapping.
2. Reuse shared status components.
3. Replace remaining color-only indicators.
4. Ensure icon shapes remain distinguishable without color.
5. Provide accessible names and screen-reader support.
6. Preserve appropriate semantic colors as supplementary information.
7. Respect `prefers-reduced-motion`.
8. Avoid unnecessary animations.
9. Display status meaning consistently across sidebar, task lists, inbox, project views, task headers and bubbles.
10. Include a visible indicator for terminal states where the design calls for it.

## Task bubbles during streaming

Investigate and fix task bubble visibility during active streaming.

Requirements:

- Create or expose the task record immediately when the authoritative task starts.
- Show the bubble before completion.
- Update it when task events are committed.
- Keep it visible through streaming, reconnection and role transitions.
- Stop the loading indicator after an authoritative terminal transition.
- Do not assume a disconnected external model has finished merely because updates are silent.
- Do not invent partial ChatGPT/Gemini output when that content was not emitted through supported tools.

Cover both internal Orchestrator tasks and external work sessions.

## Acceptance tests

Verify queued, planning, running, blocked, review, done, failed, and applicable stopped states.

Test desktop/mobile rendering, screen-reader labels, reduced motion, browser refresh, SSE reconnect, and external streaming activity.

# Phase 2 — Mandatory role assignment for external work

## Problem

Every external agent activity should have a role, but the current creation contract permits role-less work.

Previous findings:

- `begin_work` accepts optional `planned_roles`.
- `ExternalWork` is created with an empty active `RoleKey`.
- `set_role` happens separately.
- `log_message` can create legacy external timelines without an explicit work session.
- Its `role: user/assistant` means message author, not agent role.

This inconsistency must be fixed at the authoritative backend boundary.

## Required architecture

Every new executable external work request must have one valid active role before execution or work-event persistence.

Do not confuse these concepts:

- Provider identity: ChatGPT, Gemini, another MCP client
- Message author: user or assistant
- Agent role: Researcher, Planner, Developer, QA, Security or another enabled roster role
- Authorization: OAuth scope, tool permission, project ownership and server policy

These are separate dimensions.

## Required behavior

1. Inspect the existing agent roster and role-routing conventions.
2. Make initial role assignment part of the work-session creation contract.
3. Choose the initial role through a validated role-selection flow.
4. Require the external client to provide a valid initial role or an equivalent server-supported selection contract.
5. Validate against the user's enabled roster.
6. Persist the work session, initial role, and initial role event atomically.
7. Reject unknown, disabled, missing or unauthorized role assignments.
8. Never silently assign a powerful default role.
9. Forbid external clients from claiming to be the internal Orchestrator.
10. Preserve role changes through the existing `EventRole` contract.
11. Do not model external role transitions as internal `EventHandoff`.
12. Role changes must never expand tool permissions.
13. Keep provider identity independently visible in the UI.

Investigate whether server-side role auto-selection can be reliably implemented with existing routing machinery. If it cannot, provide a discoverable role-selection contract with strict server validation rather than a guessed role.

## Legacy compatibility

Legacy `log_message` workflows must not create new role-less executable requests.

Determine a safe migration or compatibility strategy that:

- Preserves historical activity records.
- Does not fabricate historical role attribution.
- Keeps read-only discovery and OAuth behavior operational.
- Does not incorrectly treat a `user` message as an agent role.
- Returns actionable compatibility errors for old clients when necessary.
- Prevents untracked execution from bypassing mandatory role attribution.

Also verify role attribution for general MCP file and command tools, not only specialized work tools.

If legacy mode is retained, it must be explicitly bounded and must not bypass the new requirement for executable work.

## Acceptance tests

- Missing initial role is rejected.
- Unknown role is rejected.
- Disabled role is rejected.
- External Orchestrator role is rejected.
- Role cannot increase privileges.
- Concurrent work sessions remain isolated.
- Role changes are accurately recorded.
- Existing historical records remain readable.
- No new executable external task is created without validated attribution.
