## Design references

- **Status icons:** WCAG says color alone cannot distinguish status. The project centralizes status labels, icons, and tones in `web/src/features/workspace/content/status.ts`; `StatusDot.svelte` adds a screen-reader label. Pair distinct icons with visible text where space allows, and keep accessible names on icon-only uses. [WCAG 2.2 Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)
- **Approval cards:** The existing `ApprovalCard.svelte` uses a compact card, names the request, reveals technical details on demand, offers explicit decision buttons, and shows a resolved state. For plan approval, apply the same structure to the exact revision and its decision; include a clear “Request changes” action. [ApprovalCard.svelte](/workspace/web/src/features/workspace/task/thread/ApprovalCard.svelte)
- **Status messages:** WCAG 2.2 AA requires status changes that do not move focus to be programmatically identifiable, so assistive technology can announce them without interrupting the user. Use a status role for concise updates such as “Ready for approval”; avoid announcing every event in a long-running timeline. [WCAG 2.2 Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)
- **Reduced motion:** Tailwind’s `motion-safe:` applies motion only when reduced motion is not requested; `motion-reduce:` can remove or simplify it. The existing `StatusDot` spin is already `motion-safe`; inspect the thread’s loading dots too. [Tailwind animation](https://tailwindcss.com/docs/animation), [Tailwind state variants](https://tailwindcss.com/docs/hover-focus-and-other-states)

## Technical references

- **MCP Go SDK v1.8.0:** The project pins `github.com/modelcontextprotocol/go-sdk v1.8.0` in `go.mod`. Register typed handlers with `mcp.AddTool`; it derives and validates input/output schemas. The existing integration test uses `mcp.NewInMemoryTransports`, connects a server and client, then calls tools and inspects structured results. Extend that pattern to verify `approve_plan` schema, scope enforcement, and its result. [SDK v1.8.0 source](https://github.com/modelcontextprotocol/go-sdk/blob/v1.8.0/mcp/server.go), [work_tools_integration_test.go](/workspace/internal/modules/coding/adapter/mcp/work_tools_integration_test.go)
- **Separate approval scope:** OAuth defines scope strings as server-defined, space-separated access ranges and recommends clients request the minimum needed. A distinct `coding:approve` scope fits the PRD’s intended separation. The app also checks per-tool switches; the repo’s current scope registry and tool definitions live in `internal/bootstrap/coding.go` and `internal/modules/coding/domain/tools.go`. Whether the new scope must also be registered in consent/token validation should be confirmed against the existing authorization path. [RFC 6749, §3.3 and §10.3](https://datatracker.ietf.org/doc/rfc6749/)
- **Outbox and idempotency:** An outbox makes the approval record and pending dispatch durable in one database transaction. Dispatch may repeat after a crash, so the consumer must be idempotent and link the outbox row uniquely to the created internal task. The repo already has idempotency keys and plan revisions in its external-work path; these are useful precedent, not an approval contract. [AWS transactional outbox guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html), [work_store.go](/workspace/internal/modules/task/adapter/sqlite/work_store.go)
- **SQLite concurrency pitfalls:** SQLite permits multiple readers but only one simultaneous writer. A deferred read transaction that later upgrades to a write can fail with `SQLITE_BUSY`; `BEGIN IMMEDIATE` acquires the write transaction earlier but can itself return busy. Use unique constraints as the final concurrency guard, keep the critical database transaction short, and handle busy/retry behavior deliberately. [SQLite transactions](https://sqlite.org/lang_transaction.html), [SQLite isolation](https://www.sqlite.org/isolation.html), [SQLite UPSERT](https://www.sqlite.org/lang_upsert.html)
- **Go transaction handling:** In Go, perform all statements in the transaction through `*sql.Tx`; mixing `*sql.DB` operations with transaction work can use another connection and break atomicity. Ensure errors roll back and successful paths commit. [Go `database/sql`](https://pkg.go.dev/database/sql#Tx)
- **Svelte 5 runes:** The project already uses typed `$props()`, `$state`, and `$derived` in its components. Use `$state` for mutable component state, `$derived` for values computed from state/props, and `$props()` for typed inputs; reserve `$effect` for synchronization or external side effects. [Svelte `$state`](https://svelte.dev/docs/svelte/$state), [Svelte `$props`](https://svelte.dev/docs/svelte/$props), [Svelte `$effect`](https://svelte.dev/docs/svelte/$effect)

## Quality checks

| Scenario | Setup and action | Expected result |
|---|---|---|
| Approval idempotency | Approve the same user/project/work/revision with the same key twice; also retry after a simulated timeout | Same approval and handoff reference; one internal task |
| Concurrent approval | Race two requests for the same revision with distinct connections | One durable approval and one linked internal task; loser receives the persisted result or a defined conflict |
| Authorization | Try read-only scope, disabled switch, wrong user/project, unverified user, and stale revision | Each is rejected; no approval or outbox row is created |
| Restart recovery | Persist a pending outbox row, restart, run startup recovery, then retry dispatch | The handoff is completed once; retries do not duplicate the internal task |
| Snapshot immutability | Approve a revision, then edit the external plan | Approved snapshot remains unchanged and handoff uses that snapshot |
| SSE replay | Disconnect after an event, reconnect with `Last-Event-ID`, then simulate a missed hub wake-up | Missing state is re-read; client deduplicates/upserts by stable ID and preserves sequence order |
| Event updates | Update an existing event/version, reconnect, and wait through heartbeat | Changed event is discoverable and UI does not show duplicate or stale content |

The SSE row is informed by the project’s existing stream and event-version paths in `internal/modules/task/adapter/http/stream.go`, `internal/modules/task/application/hub.go`, and `web/src/features/workspace/logic/thread.ts`. **Inference:** outbox recovery and replay expectations follow from the PRD’s restart and reconnect requirements plus SQLite and outbox behavior; they are not claims that these tests already exist.
