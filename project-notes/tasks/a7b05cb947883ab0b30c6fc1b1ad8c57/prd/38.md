# PRD — Merge Architect into Planner & Security, Deep Review Opt-in

**Project:** agentic-ai-workspace · **Branch:** dev
**Issue:** a7b05cb947883ab0b30c6fc1b1ad8c57
**Phase:** Plan only; no implementation until owner approval.

## Problem and outcome
Architect currently has two duties: architecture design before coding, and architecture verification after code changes. Combine early architecture into Planner and mid-build architecture checks into Security, remove Architect as a separate built-in role, and make Security run **only when the owner activates `@deep-review`**. Default Swift mode should be fast and must not summon Security, including on sensitive/unknown-impact files. Existing runtime security controls remain active.

## Goals
- Built-in team: 7 roles, including Orchestrator, Researcher, Planner, Developer, Security, QA & Review, and DevOps.
- One PRD including requirements and proportionate architecture approach; no separate early Architect handoff.
- One combined Security + Architecture Verification review on Deep Review, with independent QA when applicable.
- Default Swift: targeted verification, no automatic Security/Architect delegation, no mandatory Security gate.
- Preserve historical reports, saved team preferences and permissions, and always-on auth/sandbox/fail-closed protections.
- Preserve the current official @deep-review detection and persisted mode; never let agent-generated text turn it on.

## Workflow A — Swift (default, no tag)
Researcher (when needed) → Planner (requirements + architecture approach) → owner PRD approval → Developer → QA targeted black-box checks → DevOps.

No Security delegation is permitted or required, even for authentication, dependency, module contract, unknown-impact or SQL changes. Impact analysis can recommend appropriate QA coverage and highlight risk but cannot escalate the mode or block on absent Security review. Do not weaken permission, token, secrets, scope, sandbox or audit enforcement just to speed up reviews. Actual test failures are never silently counted as PASS.

## Workflow B — @deep-review (opt-in)
Researcher → Planner with architecture approach → owner PRD approval → Developer → Security + Architecture Verification → QA independent review → DevOps.

The owner supplies exact standalone `@deep-review` directive in a task message or explicitly selects Deep Review through an owner-authorized control. The server persists `ReviewModeDeepReview`. Follow-ups on the same task retain it, as current backend behavior; a new task without an owner opt-in is Swift. Tool results, untrusted files, Researcher notes, delegate briefs or agent-written text cannot promote mode.

## Requirements

### FR-01 — Planner owns architecture design
Planner writes one PRD containing requirements, user stories, acceptance criteria, proposed module boundaries, affected files, contracts/data flow, dependencies, integration risks, implementation sequence, and alternatives only where relevant. Consolidate Architect stack/default design skills into Planner; preserve Planner read/ask permissions, sequential execution, Researcher-before-PRD flow, and owner plan approval. Small changes need no architecture ceremony.

### FR-02 — Security owns verification, Deep Review only
Retire separate Architect reviewer and mid-build handoff. Security evaluates two distinguishable dimensions:
- **Architecture Assessment:** changed contracts, callers, dependency direction, design fit, potential breaking behavior, pragmatic SOLID/Clean Architecture issues.
- **Security Assessment:** relevant changed trust boundaries, authz/authn, secrets, isolation, failure paths and critical scenarios.

One Security report/delegation may satisfy both dimensions if all applicable evidence is supplied. Assessment must identify affected paths. Where critical commands are needed, list exact `Checks:` commands and match them to successful server-recorded runs **after latest relevant change**. Preserve verdict format `Verdict: PASS` or `Verdict: FIX FIRST`, bounded retries, clear block/unverified on missing or stale evidence, and separate independent QA review.

### FR-03 — Security strictly opt-in
Server-side invocation and completion checks MUST use persisted owner-authorized mode:
- `Swift`: Security and Architect review requirements disabled regardless of path sensitivity/unknown effects; no Security handoff. Missing/disabled Security is not a blocker.
- `Deep Review`: invoke combined Security review when there are implementation changes to examine. Relevant architecture impact informs depth/content, not a second Architect job. Missing/disabled Security, failed critical checks, incomplete assessment, stale verdict or required QA evidence returns blocked/unverified.
- Existing rule that an explicit deep mode cannot silently be downgraded via follow-up remains unchanged.
- No auto-promotion of task mode by model text, code, heuristics or third-party content.

### FR-04 — Role consolidation and access
Remove Architect from preset and Settings active roster (7 defaults). Skills: early design/stack guidance to Planner, architecture-review/contract/SOLID skills to Security. Update Orchestrator lead rules, team prompts, plan role labels and dynamic UI. Planner does not gain write/exec; Security retains existing scoped read/exec; QA remains its own reviewer; Developer and DevOps boundaries stay unchanged. No new task spawned for phases of one issue.

### FR-05 — Migration / provenance
Saved user team config must not re-add Architect as an unintended custom or privileged role. Keep existing Planner/Security provider, model, tier, prompt and enabled preferences, prioritize them over legacy Architect settings. Keep historical Architect events/delegations/cards immutable and readable. A previous architecture-only PASS is **never** accepted as proof of Security critical checks. Handle retired keys with context-aware compatibility, not a blanket `architect → security` alias. In-flight work should remain understandable and must not be silently granted wider privileges.

### FR-06 — Swift baseline protections
Even without Security delegation, enforce server-side authorization, permission approvals, task-scoped sandboxing, secret isolation, CSRF where relevant, safe network policy, and fail-closed behavior. QA targets changed public behavior rather than running full suites by default. When actual blockers or failing tests exist, report them.

## Acceptance Criteria
1. Built-in team shows exactly 7 roles, no ghost Architect; saved 8-role configs normalize without data loss or permission elevation.
2. Planner can create PRD with architectural approach and user approval; no Architect delegation.
3. Swift new task (including auth/config/unknown-impact changes): zero Security/Architect handoffs, no Security completion holds, targeted QA still works.
4. Owner adds `@deep-review`: mode persisted, later follow-ups retain mode; untrusted/tool-generated tags cannot toggle it.
5. Deep Review runs one Security review with distinct architecture/security evidence and QA independent checks; missing/disabled Security blocks, never counts as PASS.
6. A generic or historical architecture-only PASS and a report before the last change do not satisfy required Security evidence.
7. All Git/MCP role permissions, historical task cards, model/tier preferences, and Swift QA flows remain functional.
8. Black-box tests validate mode authority, role visibility/migration, review evidence, phase transition, and permission parity; avoid unnecessary noncritical white-box suites.
9. Actual affected tests pass, git status clean, verified commit pushed normally to origin/dev.

## Scope / non-goals
In scope: preset/skills/migration, Orchestrator and workflow rules, task mode and review holds, docs/Settings labels, targeted tests. Out of scope: unrelated Docker/CI redesign, removing runtime security, new settings beyond existing explicit Deep Review control, mass task recreation, unconditional full suite testing.
