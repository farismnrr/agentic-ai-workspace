# PRD — Eight-role boundary remediation + Developer Git/GitHub workflows

Original baseline: dev b038f41 (already redeployed). This PRD supersedes previous incomplete role-boundary remediation claims. Same task/work_id throughout; no child task spam.

## Roles and ownership
- **Developer:** creates source/UI/assets/documents; manages Git branches, worktrees, stash, cherry-picks, merges, rebase, commits, normal push; GitHub Issues, PR creation/updates and read-only CI status.
- **QA:** runs owner-configured black-box checks and independently reviews code; reads PR/CI status and posts GitHub PR reviews. No source modification, Git push, workflow dispatch or deploy.
- **DevOps:** builds/packages/runs apps, owns CI reruns, workflow dispatch, releases and deployments. No source edit, Developer Git push or QA test execution.
- **Planner, Researcher, Architect, Security, Orchestrator:** existing scoped responsibilities and tool access remain, with separate owner approvals.

## VCS capability
1. Expose **git** and **gh** as broadly useful direct-argv capabilities; no arbitrary shell string, no need for a different tool for every subcommand. Use existing installed sandbox git/gh and GitHub owner connection.
2. Git supports routine operations (status, diff, logs, branch, checkout, worktree, stash, fetch, pull, merge, cherry-pick, rebase, restore, commit, push, porcelain and plumbing). Separate explicitly destructive or code-executing options (force-push, remote ref deletion, hard reset, clean, custom hooks/SSH/helper/filters) from ordinary commands.
3. GitHub CLI supports `gh issue`, `gh pr`, `gh run`, `gh workflow`, `gh release`, `gh repo`, `gh search`, `gh project`, and GET-only `gh api`, authorized per operation and server-owned active role. Extensions, arbitrary API writes, repo deletion, workflow disable, PR merges and destructive operations require independent approval infrastructure; do not quietly grant them with coding:exec.
4. Git/GitHub network is scoped to the existing connected GitHub host allowance and owner credentials; Git/Gh runs get no project-env secrets or unrelated database/egress grants. Prevent terminal editors, Git hooks, dynamic external helpers and arbitrary shell interpretation wherever possible. Do not claim perfect protection against malicious repository filters without Docker/runtime proof.
5. Read-only Git/GitHub queries should not create repetitive human approval prompts; mutations follow existing approval and access rules. Preserve normal Swift defaults. Remote push success must be verified against authoritative remote refs, never inferred from a local commit.
6. Existing tool settings, OAuth scopes and one visible task remain upper bounds for internal delegated teammates and external MCP tools alike. Do not represent same-assistant self-switching as independent verification.

## Black-box acceptance
- Developer can use Git everyday actions and gh Issues/PR/CI reads; Developer cannot rerun CI, create a release, execute arbitrary shell, run QA checks or deploy.
- QA can read checks and review PR, cannot commit/push or mutate Issues. DevOps can rerun CI and dispatch workflows, cannot commit/push source or author Developer PRs.
- Destructive Git/gh options, unauthorized role operations, token-less accounts, invalid arguments and untrusted helper execution fail closed with actionable errors.
- Positive Git checkout/cherry-pick/rebase/stash/commit/fast-forward push with remote SHA comparison; gh Issue/PR/CI/release operations through connected GitHub; safe Docker/subpath negative tests when enabled.
- Go affected-package tests, project frontend validation, git diff --check, normal non-force fast-forward push to dev; preserve unrelated dirty files. If test/push tools are unavailable, report blockers explicitly instead of claiming completion.
